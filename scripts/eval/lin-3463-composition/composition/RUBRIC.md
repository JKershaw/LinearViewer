# Composition rubric (LIN-3463), written before any outcome was joined

Each file `Cnnn.json` holds one ticket as its first dispatched session found it: title, parent
identifier (if any), and the description captured at that first dispatch. Code how the ticket is
**composed**. You are blind to how the work went: do not look anything up, do not call any API, and
do not guess the outcome.

## Codes

1. `origin`: who or what most likely wrote the text. Use the text's own markers.
   - `john`: in John's own voice, first person or terse, no agent scaffolding
   - `companion`: written for John by an interactive agent session (the Flight Companion, passage
     planner or a chat): polished house prose, often "John's decision", "Why", "Done looks like",
     a `Generated by Claude Code` footer, written as a brief to another agent
   - `periodical`: a finding filed by a periodical review (Code Quality, Drift & Coherence, Test
     Coverage, Security, etc.): "From <Review> <date>, finding N", severity, ledger row
   - `follow-up`: filed by a pipeline stage about another ticket's work: a review or close-out
     follow-up, a deferred ledger item, "found while working LIN-n", residue
   - `breakdown`: a child carved out of a parent's plan or breakdown: "Part A of LIN-n", "slice",
     "carved out of", child of a plan
   - `other-agent`: another agent wrote it (autopilot, incident, research spinoff) and none of the above fits
   - `unclear`
2. `what_decided` (0–2): is the outcome settled?
   - 0: states a problem or an aim only; what must be true at the end is left to the agent
   - 1: partly: the outcome is named but a material behaviour or product choice is left open
   - 2: settled: what must be true when done, and any behaviour choice, are stated
3. `open_behaviour` (yes/no): does the ticket leave a behaviour, product or user-facing choice for
   the agent to make (including an explicit "decide whether", "either … or", "open question", or a
   change whose effect on existing behaviour is not stated)?
4. `how_prescribed` (0–3): how much of the means is prescribed?
   - 0: none: no approach, files or steps named
   - 1: pointers: names files, functions or sites as context, approach left open
   - 2: a fix: a named approach or "Fix:/Suggested fix:" the agent is expected to follow
   - 3: a program: ordered steps, an embedded plan, exact code, or tests to write, laid down in advance
5. `decisions` (integer 1–5, 5 meaning 5 or more): how many distinct decisions the ticket asks to be
   made or landed. A decision is one thing a reviewer would judge separately (one behaviour, one
   place to consolidate, one feature, one bug). A list of sites for the same decision is one.
6. `asserted_facts` (0–2): how much code fact the ticket asserts that the agent must take on trust
   or re-verify (counts, file:line sites, "today X does Y"). 0 none, 1 a few, 2 many (tables, site
   lists, counts).
7. `acceptance` (none / prose / checkable): is there a done-when? `checkable` means a test, grep,
   count or observable check is named.
8. `work_type`: bug / feature / refactor / research / docs / process / ops / other
9. `size_guess` (S/M/L): how big the change reads, from the text alone.
10. `note`: one sentence on anything about the composition that a later reader should know.

## Output

A JSON array, one object per ticket:

```json
{"id": "C001", "origin": "companion", "what_decided": 2, "open_behaviour": "no", "how_prescribed": 1,
 "decisions": 1, "asserted_facts": 2, "acceptance": "checkable", "work_type": "refactor",
 "size_guess": "M", "note": "..."}
```
