# LIN-4085 built twice: a fast session and Harbour on the same request (1 November 2026)

A record of one comparison and what it suggested, written as source material for an essay. It was
compiled by the Claude Code session that watched both runs, reconstructed Harbour's cost and ran the
blind review. Numbers are read from the dispatch records, the session usage API, the ticket trail
and git. Two verbatim evidence files sit beside it in `_evidence-2026-11-01-lin4085/`: the blind
review (`blind-review.md`) and the fast session's own run record (`fast-run-record.md`).

**In one paragraph.** John spoke an idea into a Claude Code session that was meant only for
discussion. The session built it in about 21 minutes and pushed it unasked. Instead of merging, John
gave Harbour the same words. Harbour took 59 minutes to merge and 71 to finish, across eight stages.
A blind reviewer preferred the fast session's version (30 to 27 out of 35): it had the far better
guide. But the fast session shipped a security flaw that Harbour's 4-minute independent review had
caught in its own build. Harbour's guide was thin because the request's intent narrowed at the first
handoff and every later stage, review included, checked against the narrower version. The reading
that came out of it: Harbour's stages do two jobs, making an agent capable and making it accountable.
With today's agents the first now costs more than it gives, and the second still pays.

## 1 How it started

John had an idea for the homepage: where software usually shows an install command, Harbour would
show a short prompt that a person pastes into their own coding agent. The prompt links to a guide
written for agents, so the agent can onboard the person and their projects. He dictated it into a
Claude Code cloud session to explore. Without being asked, the session researched, built, tested
and pushed a branch (`claude/relaxed-babbage-wibxgq`).

His first thought was to merge it. His second was that he shouldn't, because it hadn't been through
Harbour's process. His third was that it had taken minutes where he'd expect Harbour to take hours.
So before merging anything he gave Harbour the exact same words as a feedback item, set its
autopilot going, and asked for a comparison of the results and of the sessions themselves: where
the time and money went, what was skipped, and whether the codebase was simply well enough
structured that this kind of work could be quick.

**The request, verbatim** (voice-transcribed: "MPM" is npm, "Harper" is Harbour). Both runs got
these exact words; the slips were kept so neither run had an easier input.

> Have an idea which I think might be interesting to explore which is on the homepage the getting started section normally for software has like an MPM installed command we can have a prompt that the person passes to their agent this can be a couple of paragraphs explaining the situation and linking to a harbour.cat slash getting started page which walks an agent through onboarding project and the user to Harbour. Because it's instruction for an agent the human naturally uses the agent interact with Harper which is a good first step then because the agent can then read the guide it can decide whether to have a conversation with the user or review The repositories and the settings and we can have essentially a full guide on how to properly configure Harper for whatever your situation is without the user needing to follow those steps as the use uses the agent having naturally would.

**Stray pushes.** The fast session pushed before John's "don't push" reached it; he deleted the
branch. A second session, started only to discuss an idea, also pushed (`claude/fervent-carson-t8dzrw`,
a one-line `llms.txt` change, later a discoverability spike and epic LIN-4089). Three unrequested
pushes from two discussion sessions in one afternoon. Two causes were visible: cloud sessions start
with instructions to commit and push their work to a branch, and an end-of-turn hook flags unpushed
commits. Both stray branches were briefly visible on GitHub while Harbour ran; nothing in Harbour's
ticket trail mentions either, and the fast branch never reached this record's own clone.

## 3 The blind review

A fresh session got both changes as two unlabelled commits, the request, and a seven-part rubric,
and was told not to guess which was which. It ran both full suites, started real servers, sent
forged Host headers, checked about 40 of the guides' claims against the source, and made 46 deliberate breakages
in the code to see which tests noticed. Full report: `_evidence-2026-11-01-lin4085/blind-review.md`.

| Dimension | Harbour | Fast session |
|---|---|---|
| Fidelity to the request | 3 | **5** |
| Correctness of the guide's claims | 4 | **5** |
| Security | **5** | 4 |
| Test quality | 4 | 4 |
| Fit with the codebase | **5** | 3 |
| Agent usability | 3 | **5** |
| Simplicity and scope | 3 | **4** |
| **Total** | 27 | **30** |

- **Fast session:** "the implementation that delivers the feature as asked". About 28 claims checked,
  none false. Its worst defect: the homepage prompt was built from the raw Host header, so a forged
  header put an attacker's address into the prompt a person copies into their agent. Harbour's
  review had flagged exactly this area in Harbour's own build. Also: three route checks that matched
  any mention of a path, and no size limit on the guide.
- **Harbour:** "the better-engineered shell": a validated origin with a running-server test, the
  sign-in list generated from the hero's own, size ceilings, a guard against an existing
  token-minting copy handler. But "the guide is too thin for the request", and three of its claims
  mislead (for example, that prompts need an OpenRouter key when the free tier is off, though
  template steps need none).
- **Verdict:** merge the fast session's version after fixes, or better, its guide and drift tests on
  Harbour's code. That combination is now LIN-4090.

Limits: one task, one reviewer, partial blinding (Harbour's side cites LIN-4085 31 times).

## 4 What it showed

1. **The request's intent was lost at the first handoff, and every later check approved what was
   left.** Scoping wrote "the guide's job is to sequence the human's few clicks" over "a full guide
   on how to properly configure Harbour". The success criteria were mechanical (returns 200,
   placeholders filled, links resolve). The plan put the guide under a 4.5 KB budget. Review's verdict
   was "the deliverable meets the plan". Only the blind reviewer, reading the original words, saw
   the gap. Each fresh stage did its job well with what the ticket gave it.
2. **Independent checking was cheap and decisive.** Plan-review and review took about 6 of the 71
   minutes. Review caught that Harbour's own origin check had no forged-Host test, the class of defect the fast session left in, after the fast session had
   checked its own work thoroughly.
3. **Continuous building produced the better product.** One session with the whole picture, fed by
   two research subagents, wrote a guide about six times longer with no false claims found.
4. **A rule applied outside its purpose shaped the result.** The prompt-size budget exists to bound
   text that every dispatched stage pays for. Applied to a public guide read once per onboarding, it
   boxed the guide to about 4.5 KB. The fresh blind reviewer then marked the fast session down for
   not following it. Fresh agents read rules literally, so a rule needs its purpose stated.
5. **Harbour took about an hour, not hours, and much of the difference is landing work.** Like for
   like (to a pushed branch with tests green) it was roughly 21 minutes against 45. The rest was
   merging, CI, deploying and checking production, which the fast session never did.
6. **The costs look similar, but Harbour's could not be measured.**
7. **Sessions meant for discussion ship code**, for the reasons in section 1.

## 5 What it might mean

**Two jobs in one pipeline.** Harbour's stages do two jobs that are bundled together. One is making an
agent *capable*: splitting a task into research, plan and build, each a fresh session that does one
part well. The other is making it *accountable*: independent judges, rulings, landing with production
checks, and a record of every run. With today's agents, the first job costs more than it gives (the
splitting is what lost the intent and paid for re-orientation at every hop). The second still pays
(a strong agent alone produced the better product and still shipped the flaw a fresh review caught).
The August lane review reached the same split from the other side: "Production is continuous;
verification is independent", and the stepper's "capability-substitution half is plausibly
unnecessary at the frontier".

**A record problem more than a memory problem.** The `held-or-fresh` paper found, for supervisors,
that no sampled decision rested on a fact only a session's memory held, and that holding a session
and starting fresh cost about the same; the saving came from a fresh step reading a small, good
handoff. LIN-4085's fresh sessions read the ticket faithfully. What failed was the record: scoping's
narrower version replaced the request. So the first fix is cheap: keep the request as filed on the
ticket, give it to every judge, and turn any narrowing into a ruling for a person.

**A continuous session as a cache over the record.** One warm session could hold a task from research
to fixes, with fresh judges branching off at the gates (plan-review after the plan, review on the
PR), each given the original request, sending findings back one way. Harbour lands the work. Named
in conversation as *spine and branches*.
- It adds speed and keeps what records rarely hold: dead ends, approaches ruled out, familiarity with
  the code. Sessions re-find a lot: about 26% of tokens go on orientation, and 53% of what a session
  reads while orienting, an earlier session on the same ticket had already read (`starting-context`).
- It costs more per step as history grows, it can hold stale beliefs (so it should re-check itself
  against the code and the request at each gate), and it removes one cross-check (a fresh builder
  distrusting the plan).
- It is as safe as today's pipeline only if the judges stay fresh and their verdict, not the
  builder, decides whether work lands, and if the record stays complete enough to restart from.
- Harbour already has most of it. The stepper (`variant: stepper`, LIN-788) drives one warm session
  through 3–6 beats, judged by the orchestrator, and never chains into review "to keep the
  fresh-eyes boundary". It would need to span stages and put fresh judges at the gates.

**Five run shapes on one axis** (who holds the context while building, and who judges):
relay (Harbour today, a fresh session per stage); lane (one long session, many tickets, self-review;
8 of 50 later failed independent review); stepper (one warm session, beats, orchestrator judges,
review stays fresh); spine and branches (one warm builder, fresh judges with the request, Harbour
lands); any builder (work made anywhere arrives as a branch and a ticket, and Harbour checks it
against intent, reviews it and lands it; LIN-4090 is the first case).

**Messages between sessions.** The channels exist: a follow-up into a held session (it arrives at the
next stop, never mid-turn), a wake up the chain when a child stops, a ruling to a person, ticket
comments as the durable record, and direct messages between live sessions. One rule keeps
independence: advisers may converse, judges only report. Advisers can be reused across tasks; judges
rotate so nobody reviews work they shaped.

**Harbour's utility.** Building is becoming a commodity: every vendor's agent is getting better at it.
Independence is structural: a model reviewing its own work is still self-review, however good the
model. And verification cost is the gate the `where-harbour-joins` paper names as unmoved since March.
So Harbour's value shifts from helping agents do the work to making agents' work trustworthy:
keeping intent intact, judging independently, landing with proof, measuring across runs, and
accepting work from any builder. The landing page's line already says it: "keep human intent in
command of AI execution". What would shrink: splitting production across fresh sessions, much of
the building-prompt scaffolding, and dispatch churn (LIN-3891 measured 7 to 27 dispatches per
ticket). Risks: vendors may build review into their own agents, and this rests on one task.

## 7 Limits

One task, one blind reviewer, partial blinding. Harbour's cost is reconstructed, not measured. The
fast session ran with John's words fresh and no ticket to read; Harbour's stages read the ticket as
it evolved. `replay-small-work` warns that a lean pipeline matched the full one only with hindsight.
