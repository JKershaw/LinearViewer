# LIN-260 — Scaling prompt complexity & output to task scale (research)

> Status: **research / not yet implemented.** This document is the saved analysis
> for [LIN-260](https://linear.app/linearviewer/issue/LIN-260/scale-prompt-complexity-and-output-on-task-scale).
> It captures what the prompt system does today, why uniform sizing happens, the
> recommended approach (lower + upper bound), the Surface Assessment, and a
> discussion of *what kind of change this actually is* (prompt tuning vs.
> structural). Re-grounded at HEAD — the prompt system churned ~20 commits since
> mid-May, so this is read off current source, not the ticket's original framing.

## The problem

Outputs are uniformly sized regardless of the task's actual scale. A single-line
change goes through the same heavy prompts and processes as a substantial change.
Two bounds, from the ticket + John's comments:

- **Lower bound:** small tasks shouldn't trigger heavy prompts/processes.
- **Upper bound:** large *upstream* outputs shouldn't inflate *downstream*
  prompts/outputs — and a prompt shouldn't do the next agent's job. John's
  examples: (a) a deep research piece makes the plan get written in the same
  in-depth style, expanding a simple plan and opening room for errors/hallucination;
  (b) a long "plan is the next step" prompt gives so much detail it writes out the
  plan itself — which is the next agent's job.

## Key findings

### 1. Sizing is static, in two synced paths

Prompts are generated by:

- **Handwritten:** `generatePrompt()` (`lib/prompt-templates.js`) → static
  `sections` arrays in `lib/prompt-template-defs.js` (15 templates) + shared blocks
  in `lib/prompt-formatters.js`.
- **AI-generated:** `buildMetaPromptTemplate()` (`lib/prompts/meta-prompt-template.js`),
  consumed by `/recommend` in `lib/openrouter.js`.

CLAUDE.md's both-paths rule keeps them in lockstep. Each template emits a **fixed
scaffold regardless of task scale** — the plan template is ~80 lines for a one-line
fix or an epic alike; the meta-prompt's plan quality rule
(`meta-prompt-template.js:203`) is one unconditional ~400-word paragraph applied to
every plan. **No scale signal gates length.** `estimate` / `priority` /
description-length are consumed nowhere in generation.

### 2. The phases

`blocked, bug, plan, code-review, look-into, triage, breakdown, research, scoping,
design, spike, context, implementation, review, retro`. Core dev arc:
research → plan → breakdown → implementation → review. The autopilot loop chains
them (`/recommend` → dispatch → worker → write-back to Linear → next `/recommend`);
the orchestrator never sees the prompt (the prompt is generated and dispatched
without passing through it).

### 3. Depth propagates through the Linear write-back (the upper-bound mechanism)

Each phase writes its output to the Linear **description** + **comments**. The next
phase's prompt re-injects the **full description and ALL comments verbatim** —
`formatComments()` (`prompt-formatters.js:105`) and `formatCommentsForPrompt()`
(`openrouter.js:223`) do no summarization, truncation, or budgeting. So a deep
research artifact lands in comments → the plan prompt's Context block now contains
the whole research write-up → the plan inherits its depth.

The amplifier is the meta-prompt **Grounding Rule** (`meta-prompt-template.js:76-78`):
*"the generated prompt must only contain information explicitly present in the Task
Context."* It was built to **stop hallucination**. But once research has dumped a
plan-shaped artifact into context, that detail *is* "explicitly present," so the
meta-prompt faithfully restates it and **writes the plan that was the plan-agent's
job.** This is John's "long 'plan is the next step' prompt writes the plan itself,"
and it is locatable at the Grounding-Rule × full-comment-dump intersection.

### 4. Scale signals available

- **Best:** the plan's own **session-fit answer** (`fits one session` /
  `needs multiple sessions`, `meta-prompt-template.js:122-128`) — the one explicit
  scale decision the system already produces. It is used only to route the
  *workflow* (plan→impl vs plan→breakdown), never to size output.
- **Secondary (reliable):** child/subtask count; epic-shape
  (`isEpicShapedParent`: ≥4 children or a phase/migration/epic title).
- **Noisy:** `estimate` (sparse, often unset); description length (a terse ticket
  can be huge work, a verbose one trivial).

### 5. Existing guards, and why they fall short

- **The one real precedent:** retro's "Scale to the task" block
  (`prompt-template-defs.js:885-887`) — *"a small leaf task gets a short, focused
  retro… for an epic, aggregate across children."* Proof the team already accepts
  per-phase depth scaling — but it's bespoke prose in one template, keyed off
  structural position, not a reusable mechanism or an explicit scale signal.
- **Context-inclusion caps, not output-sizing:** `RECOMMENDATION_MAX_TOKENS=8000`,
  `SIBLING_CAP=5`, `COUSIN_CAP=20`, `EPIC_CHILD_THRESHOLD=4` (`openrouter.js`). They
  bound how much *upstream context* is rendered but never how big the *generated
  prompt/output* is — and they don't touch comments (dumped in full).
- **Routing guards, not sizing:** the research over-firing guard (Step 1) keeps
  trivial tasks *out* of research, but once any phase is entered its template is
  full-size.

## Recommended approach (for the plan phase to act on)

Handle the two bounds with different mechanisms; lead with the upper bound (it's the
live pain and needs no scale signal).

### Upper bound — stop depth propagating / prompts doing the next agent's job

- **Explicit phase hand-off ("stay in your lane") contract** in BOTH paths:
  *produce your own artifact; do NOT produce the next phase's.* Research ends at a
  recommended approach + Surface Assessment and must NOT write the implementation
  plan; plan enumerates surfaces/arrows/session-fit and must NOT write
  implementation-level steps. This gives the Grounding Rule's "restate what's
  present" a counter-force it currently lacks.
- **Bound what downstream inherits.** Add a seam so phase-to-phase context is a
  *distilled hand-off*, not every comment verbatim. The primitive already exists —
  the `/brief` endpoint (Current / Constraints / Open-questions / Changelog,
  "supersedes stale wording, folds in comments"). Routing the Context block through
  brief-style distillation stops a deep research piece from dragging the plan into
  its style.

### Lower bound — small tasks shouldn't trigger heavy prompts

- **Use the session-fit answer as the scale signal** (already exists, already
  trusted for routing). When a plan is `fits one session` / single-surface, the
  downstream implementation & review prompts collapse to a light scaffold. For the
  plan phase itself on an obviously-small task, state explicitly that a few-line
  plan is a valid result (the Scope Assessment already half-says this — "a genuinely
  single-surface change is a valid result") so the agent doesn't pad to fill the
  scaffold.
- **Generalize retro's "Scale to the task" into a shared block** (mirroring the
  `formatStalenessCheck()` shared-block pattern) consumed by both paths, so
  depth-matching is a reusable directive rather than one template's prose.

**Net:** a `small | standard | large` scale resolved once (from session-fit + child
count, estimate as a weak tiebreaker) selects a light vs full scaffold; a
lane-boundary line per phase prevents bleed-through; a distilled hand-off caps
inheritance. Bidirectional by construction — not so little that quality drops, not
so much that downstream inflates or the prompt does the next agent's work.

## Surface Assessment

**Surface Assessment: [refactor needed: three small structural seams must exist
before the scaling logic can land cleanly — all follow patterns the codebase
already uses, so this is scoped prep, not a rewrite].**

1. **A single sizing decision point.** Verbosity is hard-coded into each template's
   static `sections` array (handwritten) and into one monolithic quality-rule
   paragraph (`meta-prompt-template.js:203`) — there is nowhere to decide size once.
   Extract a `resolveTaskScale(issue, context)` (→ `small|standard|large` from
   session-fit answer + child count + estimate) plus a shared depth / `scaleToTask`
   directive block, consumed by BOTH `generatePrompt()` and the meta-prompt — the
   shared-block pattern already used by `formatStalenessCheck()` and the code-review
   toggles.
2. **A first-class phase hand-off boundary.** Phases are defined only by their
   template today; nothing but the soft Grounding Rule stops research from writing
   the plan. Add an explicit lane-boundary line to each template + each meta-prompt
   quality rule (cheap, both-paths, mirrors the existing per-phase quality rules).
3. **A context hand-off seam.** `formatComments()` / `formatCommentsForPrompt()`
   dump everything verbatim with no insertion point for distillation. Add one
   hand-off-context function the Context blocks call, so propagation can later be
   bounded (swap raw comments for `/brief`-style distillation) without editing all
   15 templates.

Without these seams the scaling change would be smeared by hand across 15 templates
+ the meta-prompt paragraph and would drift between the two paths (the exact failure
CLAUDE.md's both-paths rule warns against). With them, the plan step's scaling work
lands in one resolver + one shared block + a handful of one-line lane boundaries.

## Discussion: what kind of change is this? (prompt tuning vs. structure)

Framing question: *is this pure, careful prompt tuning — making explicit the shape
of things so the right scale/translation occurs?* Mostly yes — with one seam that
crosses into structure, and that seam is load-bearing.

### The principle

An LLM, given a context and no explicit boundary, **matches the shape it was
handed** — it mirrors the register, depth, and length of its input. So uniform
sizing isn't the model being dumb; it's the model being *faithful to the wrong
reference*. It scales to the **scaffold** (80-line template → 80-line-shaped plan)
and to the **context** (deep research dump → deep plan), instead of to the **task**
(one-line change → one line of plan).

The system's real shape is currently *implicit*: the scale exists but is never
named; the phase boundaries exist but nothing states them except the soft Grounding
Rule; the translation between phases exists but is "paste everything verbatim." Each
recommendation is the same move — **make something the system already has
implicitly explicit, so the model has the true reference to scale/translate
against.**

### The three seams are not equally "prompt"

- **Lane boundaries — pure prompt tuning.** Sentences added to templates and
  quality rules ("produce X; do NOT produce X+1"). Makes the phase *contract*
  explicit.
- **Scale signal — prompt tuning with a hair of logic.** Resolving
  `small|standard|large` is a few lines of mechanical reading, but what it *selects*
  is prompt text and the directive ("a few-line plan is valid") is pure wording.
- **Distilled hand-off — crosses into structure.** Routing context through
  `/brief`-style distillation changes *what data exists in the window* before the
  model reads it. That's information architecture, not wording.

### Where prompt tuning hits its limit

Two forces act on the model:

- **Directives** govern what it is *asked* to do.
- **Context** governs what it is *pulled* to do.

When they conflict, **context usually wins.** You can tell a planner "be brief," but
if its window is full of a deep research dump it mirrors that depth anyway — the
gravity of context beats the instruction. Therefore:

- The **lower bound is very tractable by prompt** (telling a model "small is fine,
  don't pad" works — no contrary pull).
- The **upper bound is only partly tractable by prompt** — you're fighting the
  strongest pull the model has, to match its input. You cannot reliably instruct a
  model to *un-see* depth sitting in its context. The robust lever is mechanical:
  don't put the depth in front of it. **Seam #3 is that cut; the lane-boundary
  directive is the backstop, not the primary fix.**

So: prompt tuning *plus one structural cut at the propagation point*, and the cut is
load-bearing precisely because prompts are weak against context gravity.

### Why "careful" is the operative word

- **The bidirectional constraint is delicate.** Scale down too hard and you lose
  real quality on a task that *looked* small but wasn't (length is a noisy proxy).
  Lean on the **session-fit answer** — a scale signal the system *earns* by
  reasoning — not on surface features. Making shape explicit is only safe when the
  shape you assert is true.
- **The repo already encodes this discipline.** `docs/prompt-change-validation.md`
  mandates the both-paths rule, overfitting guards (write the directive abstractly,
  test against 3–4 unlike tickets), and an offline A/B eval
  (`scripts/eval-completeness-check.mjs`). Retro's "Scale to the task" is a working
  precedent — scales depth by structural position *with a guard*. The move is
  proven; the care is in generalizing it without overfitting to that one example.

### Bottom line

At its heart this is careful prompt work that makes the implicit shape of the
workflow legible, so the model scales and translates to the *task* instead of to the
*scaffold and context it was handed*. The single exception — and the part to flag
hardest for the plan step — is that the upper bound needs a real structural cut at
the hand-off, because a directive alone can't hold against the pull of a full
context window.
