Scope: the two-path prompt system (handwritten + meta) and the both-paths update rule. Moved verbatim from CLAUDE.md (LIN-2896).

### Prompt System (two independent paths)

Changes to prompt behavior (feature flags, workflow instructions, context formatting) must update BOTH:

- **Handwritten prompts**: `lib/prompt-templates.js` → `generatePrompt()` — deterministic, template-based
- **AI-generated prompts**: `lib/openrouter.js` → `lib/prompts/meta-prompt-template.js` — LLM generates via meta-prompt

**Two layers: rules assembled by code, the brief written by a model (LIN-3292/LIN-3293).** `generatePrompt()` is the template body plus `finishStagePrompt(body, kind, …)` (`lib/prompt-templates.js`), which appends everything code adds after a body, in order: the **stage contract**, grounding, attachments, the code-review sections and the capability pass. The contract (`formatStageContract`, `lib/prompt-contract.js`) carries every format a later step parses, each tested against its reader: the plan's `## Implementation Plan` heading, session-fit phrase and `plan-review due:` line; plan-review's `### Plan Review Verdict` header and verdict line; implementation's PR URL; review's title, head sha, CI line, ledger and verdict forms; close-out's title and the literals its prune keeps. It is appended on BOTH paths whatever the switch says (the meta path's `applyGroundingToRecommendation` puts it before the grounding), a read-only tracker gets none, and no template or meta-prompt rule asks for the same formats any more, so each is said once. A change to a machine-read format is a contract change: edit `CONTRACT_LINES` and its reader test (`tests/unit/prompt-contract.test.js`), not prose.

With the **`HARBOUR_BRIEF_WRITER`** environment switch on (off by default, read at call time), the meta path splits in two. The meta call routes only (`buildMetaPromptTemplate({ routingOnly: true })`: facts, decision tree, vocabulary and reasoning format, no skeleton, quality rules or `## Prompt`), the routed stage's template body becomes the rules bundle, a second model call (`writeBrief`, `lib/openrouter.js`; its prompt and every stage's ideal shape in `lib/prompts/brief-writer.js`) turns the bundle into a plain brief given the router's reasoning, and `finishStagePrompt` finishes it, so the writer can never break a gate. `defer` skips the writer; any writer failure, truncation, timeout or missing time before the hop deadline ships the unwritten bundle, which is exactly `generatePrompt()` for that stage. The writer's calls are recorded under the `recommend-write` feature, and the prompt trace records its model and outcome. It is wired on the proxy recommend path (`computeRecommendation`, behind GET recommend and recommend-and-dispatch); the UI recommend routes and the handwritten verb-override do not pass it yet. With the switch off, output is today's (with the contract), byte for byte. **Both-paths consequence:** with the writer on, the template body IS the meta path's rules, so a rule changed in `lib/prompt-template-defs.js` reaches both paths; the meta-prompt's quality rules still govern the switch-off path and must keep being mirrored until it is retired. The writer's own text is a frozen surface (`BRIEF_WRITER_SOURCE_CEILING`).

**Deterministic grounding sections are a single shared post-pass (LIN-435), not duplicated prose.** Four rules — the staleness check, terminal-state note, all-subtasks-complete note, and bug-already-investigated note — are appended by `appendGroundingSections(prompt, issue, context, kind)` (`lib/prompt-formatters.js`), which BOTH paths run as a post-pass over their rendered body: the handwritten path calls it in `generatePrompt()`; the AI meta-prompt path calls `applyGroundingToRecommendation(structured, issue, context, …)` (`lib/openrouter.js`) on the LLM's parsed `## Prompt` output at the three recommendation seams (`getRecommendation` return, the streaming branch, and — via the streamed prompt delta — the leaf view). The rule therefore executes ONCE for both paths (mirroring the capability-awareness post-pass below), so the meta-prompt no longer re-types these rules as prose and they cannot drift. The notes are chosen per stage, not appended to every template (LIN-3296): `GROUNDING_BY_KIND`, next to `appendGroundingSections`, lists which notes each template kind gets (the handwritten path passes its template key; the meta path maps the recommended action through `deriveDispatchKind`), so a look-back (`retro`, `retrospective-audit`) or read-only stage is never told to close out or implement the fix, `triage` gets none, and the bug-investigated note goes to `implementation` only. A kind not in the table (custom, or an unparsed action) keeps every note. Skipped for `defer` replies (`prompt === null`, the no-body cost contract); the pure parser `parseRecommendationResponse` stays free of `issue`/`context`. This is what fixed the meta path's broken staleness `--since` date (now injected deterministically from `issue.createdAt`, never a placeholder). Cross-path parity is pinned by the grounding-parity tests in `tests/unit/prompt-templates.test.js`.

The ticket staleness check (re-ground against current code: list referenced files/symbols, `git log --since=<createdAt>`, re-read source at HEAD before trusting the ticket) is `formatStalenessCheck()`, appended via the shared post-pass above.

The plan-fidelity check (LIN-698 — the *symmetric* counterpart of the staleness check, one stage earlier in the pipeline: the staleness check distrusts the ticket's claims about the **code** and re-grounds them against HEAD; this distrusts the plan's claims about the **research** and re-grounds them against the research/exploration notes + comment thread the plan was distilled from — surface, don't silently absorb, anything the plan dropped or contradicted, and on conflict the research's reasoning wins) is `formatPlanFidelityCheck()` in `lib/prompt-formatters.js`. It is **implementation-specific**, so unlike the four universal grounding rules it is **NOT** routed through `appendGroundingSections()` (that seam is byte-identical-pinned across all templates; plan-fidelity would leak everywhere and break the grounding-parity test) — instead the handwritten implementation template calls it inline, and the same directive (plus the adjacent refactor/behavior-preservation equivalence check: don't trust a "refactor"/"behavior-preserving" label, enumerate and verify the old behaviors, ideally via a characterization test) is mirrored in the meta-prompt's "Implementation prompts" rule. Both paths are pinned by the LIN-698 tests in `tests/unit/prompt-templates.test.js`.

The terminal-state *body note* (LIN-353 — a Done/Canceled/Duplicate task with no open children is not redone as if unstarted) is `formatTerminalStateNote()`, also via the shared post-pass; it and the all-subtasks-complete note ask what the stage they reach does (LIN-3292): review checks the work and puts what is missing in its verdict, close-out lands it and sends what is missing back to implementation, and a work stage routing sent a finished task to fixes what it was sent for at its cause. Neither tells any stage to file what is missing as a follow-up. Its *recommender routing* counterpart — the meta-prompt's "Step 0" decision branch that selects the `review` action — remains in the meta-prompt, because action selection is a meta-path-only concern the handwritten path has no equivalent of. (The deterministic descent guard that refuses defers into terminal nodes is separate, in `lib/recommend-recurse.js`.)

The bug-already-investigated *body note* (LIN-366 — a `bug`-labelled task with prior investigation in its comments advances to the fix instead of re-recommending investigation, because the `bug` label alone is not a reason to re-investigate) is `formatBugInvestigatedNote()`, via the shared post-pass; its *routing* counterpart — the "First check whether the bug has already been investigated" escape hatch in the meta-prompt's Step 2 — remains in the meta-prompt for action selection. It is a soft signal (no deterministic "investigated" marker exists; findings live in free-form comments), gated on `bug` label + ≥1 comment.

The class check (LIN-313 — "widen the model, don't patch the witness": once a bug's root cause is in hand, or before a review approves the close, ask whether the work is an isolated instance or one of a class with unhandled siblings) lives in BOTH paths — woven into the bug template's investigation steps and the review template's "Isolated, or One of a Class?" section in `lib/prompt-template-defs.js`, and the Bug-prompts rule + Review-prompts rule (5) in the meta-prompt's quality rules. Since LIN-3291 the proposed fix is at the cause: a found class is named and the fix reaches its instances at their shared cause, refactoring where that simplifies the code, and a genuinely isolated result is explicitly valid. It is the execution-altitude sibling of the plan template's Completeness check (LIN-295).

The class-not-member enumeration rule (LIN-1871, revising LIN-1873) lives in ALL THREE of the research, plan, and plan-review templates in `lib/prompt-template-defs.js`, and the matching Research-prompts, Plan-prompts and Plan-review-prompts rules in the meta-prompt. Research names each **class** the ticket touches, how it bounded it, and every member it found — bounding is reasoning (the state machine, the callers, what has landed since the grounding sha, or a grep where a grep is the honest tool), of which a **reproducible query whose output IS the enumeration** (an `rg`/`grep` pattern, an AST query, or a test that fails on an unhandled member) is one way, and the strongest one where it applies. Plan works FROM research's classes: it maps every member research found to in- or out-of-scope, and adds a class of its own only if it can say why research missed it. Plan-review argues the class a missing member belongs to, not the member alone: a reviewer who finds a member the plan lacks must say what class it belongs to, how they bounded that class, and every other member that bounding found — one round, whole class; a verdict that names a member and stops is incomplete, however correct the member. **The send-back rule follows from this**: a plan is sent back for a missing or wrongly-bounded CLASS, never for a missing member inside a class already correctly bounded. LIN-1871 measured the cost of the earlier, member-by-member shape's absence of this rule: four tickets parked at plan-review with 4+ agent sessions each and zero commits between them, where the convergent query was one `rg` or a ~40-line script in every case; `docs/papers/harbour/review-loops.md` (LIN-2800) later measured that even WITH the original cited-sweep rule, 33 of 94 tickets still went round plan-review two or more times — a member-level "cite the query" rule converges the query dispute but not the round count, which is what moved this to argue-the-class. **Two halves, and the second is what stops the first becoming a box to tick**: some classes have no sweep, and saying so is a first-class answer — the *destinations* of new or moved code cannot be swept from code that does not exist yet, and a class whose population is production data needs a corpus query rather than a repo one. **Both shapes share the property that IS the criterion for any third one named: the members are not in the current source tree at all**, so no query over it could enumerate them — a class that is merely awkward to grep (spread across names, split over files) does NOT qualify, because that is a harder query rather than an absent one. Without that criterion the hatch is an unbounded opt-out of the whole rule. A plan naming which shape applies plus what bounded the class instead is a clean pass; the reviewer checks the REASON rather than the absence, and may demand a sweep only by naming the query that would produce one. The class, its bound and its members are recorded in the issue description, where plan-review's check (1) goes looking for them. All three templates explicitly warn against manufacturing a query, a script, or a checklist to fill the slot — the rule asks for reasoning shown, not a form filled — since one that looks authoritative and is quietly incomplete ends the conversation with the wrong answer. `lib/plan-review-round-trips.js` (LIN-1883) is the round-trips instrument this change is judged against: LIN-1871 also dropped that module's own stale "0-vs-1, not 0-vs-2" header assumption (the counting was never actually capped, only the prose claimed it was) and added an opt-in `options.windowDays` calendar-window read, distinct from `routes/dashboard.js`'s row-count-capped `EFFORT_READOUT_HISTORY_LIMIT`. Pinned by the LIN-1871 tests in `tests/unit/prompt-templates.test.js`, `tests/unit/openrouter.test.js`, and `tests/unit/plan-review-round-trips.test.js`, each path failing independently.

The plan-additions rule (LIN-3202, menu M14) lives in BOTH paths — the plan template's Goal list in `lib/prompt-template-defs.js` and the meta-prompt's Plan-prompts quality rule in `lib/prompts/meta-prompt-template.js`, sited next to the class-not-member and completeness sentences so the two read as one instruction. A plan is an addition to the research, not a copy of it: it states what it adds beyond the research — the design, the steps, the tests, the scope decisions, and any disagreement with the research and why — and cites the research findings it relies on instead of restating them, by comment (author/heading or id), file:line, or sha, so a reader — including a breakdown child (LIN-3049) that receives only a copied plan slice and not the parent's research comments — can resolve the citation without the plan paraphrasing it. The citation is resolvable, never a bare "see research". Where there is no prior research the plan stands alone, with no citations to manufacture, and a finding must not be restated to make the plan self-contained; a disagreement with a finding, or a finding found stale, is stated explicitly with the evidence, as an addition rather than a restatement. The in/out-of-scope verdict for each member stays the plan's own decision (LIN-1871): "cite, don't restate" does not turn the class-not-member mapping into a bare pointer, and the class bound, the plan-review gate line and the inherited plan slice are unchanged. The evidence base is the median plan's ~440 restated words (`docs/papers/harbour/step-overlap.md` v2 B) and the checked menu M14 (`docs/papers/harbour/steady-base-menu.md` v2). Pinned by the LIN-3202 tests in `tests/unit/prompt-templates.test.js` and `tests/unit/openrouter.test.js`, each path failing independently; the plan template is not in the `appendGroundingSections` byte-identical post-pass, so no parity test moves.

**The file-pointer pilot (LIN-3200, menu M10) is a seam DOWNSTREAM of both prompt paths, not a template edit.** A short pointer is PREPENDED at dispatch time (lib/dispatch-factory.js step 7.6) to the **implementation** prompt only, on every second eligible implementation dispatch chosen deterministically from the live ordinal. It is built from two inputs already in the record: the plan's named paths, parsed from the issue description's `## Implementation Plan` block (heading matched by PREFIX, last match wins, because real headings carry suffixes), and the files edited in earlier PRs on the ticket, read from GitHub at dispatch time (lib/github-pr-files.js) because only the PR URL is recorded. The pointer never carries commit shas and no literal tracker name. Reviewers are excluded by EFFECTIVE KIND: the step's gate is `effectiveKind === 'implementation'` (plus fresh, issue-scoped, non-abort, non-follow-up), so review/plan-review/close-out/plan/research/triage/autopilot/custom output is byte-identical, and reviewer independence — a reviewer steered to the implementer's files may stop looking elsewhere — is preserved. **Preview and copied prompts are the control form**: they enqueue nothing, decide no arm, and are untouched. The arm rule is recomputable from existing row fields (`kind`, `followUpTo`, `abort`, `issueIdentifier`, `dispatchedAt`, `resolvedAt`) and adds NO row field; `addItem`'s argument is byte-identical in every arm except a delivered pointer. The arm is the ordinal parity over the lifetime retained eligible set: even ⇒ pointer, odd ⇒ control (lib/file-pointer.js `selectPilotArm`). Its limits are named, not claimed away: **R1** a count/read failure is fail-open (untouched prompt, unflaggable from rows); **R2** a store hop that outlasts `HOP_ALLOWANCE_MS`, and its write-side twin the insert lag from `addItem`'s `dispatchedAt` stamp to its visible `insertOne` above `RACE_SUSPECT_WINDOW_MS − COUNT_TIMEOUT_MS`; **R3** a swallowed archive failure (both `Error archiving dispatch item:` from `_archiveItem` and `Error archiving expired items:` from `cleanup()`'s skipped archive loop) removes a row from both collections; **R4** clock skew above `SKEW_SLACK_MS`. The read (scripts/file-pointer-read.mjs) excludes race-suspect rows from the primary comparison in both arms. The recompute depends on **LIN-3163's lifetime history retention** (`c572a681`); if retention is ever bounded again the recompute is invalid after the first trimmed row and the comparison restarts.

 **Every prompt-template change — not just this one — lands with a row in `scripts/prompt-template-change-log.md`** (John's 2026-08-04 ruling on LIN-1661; definitional home LIN-1662): date, commit sha, ticket, both paths named separately, a one-line behavioural description, and an expected direction (`up`/`down`/`unknown`) recorded BEFORE the follow-on-ratio read, so a direction cannot be rationalised after the number arrives. The follow-on-ratio measurement (`scripts/follow-on-ratio.mjs`) is protected by RECORDING changes, never by freezing them — the 2026-08-04 ruling withdrew the freeze outright ("the read stands, the abstinence does not"), and John's 2026-09-04 ruling confirmed the later Flight Companion extension defers only the read. When appending, use the re-runnable query recorded in the change log itself: a bare `git log --since=<date>` is git *approxidate* and silently drops commits from earlier in that day.

The mutation-check directive (LIN-2274 — before approving a close, a reviewer must mutation-check the load-bearing new/changed tests for at least the deliverable's own claimed behavior: delete or comment out the code path each one claims to cover, confirm it goes red, then restore it — "the test exists and asserts something" is not proof it asserts the *right* thing) lives in BOTH paths — the review template's `### Test Quality Check` section (a guideline bullet, immediately before `### Review Checklist`; since LIN-3293 the checklist no longer repeats it), in `lib/prompt-template-defs.js`, and the meta-prompt's Review-prompts rule (4) in `lib/prompts/meta-prompt-template.js`. It is the review-side counterpart of LIN-2219's acceptance-witness discipline one stage earlier in the pipeline (implementation template guideline 6 / meta-prompt Implementation-prompts rule (10)): LIN-2219 asks the *implementer* to mutation-check their own new tests before trusting them; LIN-2274 asks the *reviewer* to independently mutation-check *load-bearing* tests before approving the close — closing the gap where "the test exists and asserts something" was accepted as proof it asserts the right thing. Both paths are pinned by the LIN-2303 tests in `tests/unit/prompt-templates.test.js` and `tests/unit/openrouter.test.js`.

The review→close-out split (LIN-550) makes close-out a first-class step distinct from `review`, so the irreversible finish has an owner and a gate. `review` is now **write-only**: it appends a `### What CI Did Not Prove` ledger (the "Not-Proven-by-CI" handoff — every claim the deliverable depends on that green CI does not exercise) to its summary comment and issues a verdict that is **conditional** when the ledger is non-empty (`Approve — conditional on close-out discharging the ledger`, never a bare Approve); it does NOT merge, set Done, or file close-out follow-ups. The new `close-out` template (`category: UNIVERSAL`, key `close-out`) **consumes** that ledger and owns the irreversible set: it BLOCKS merge/Done until every ledger item is discharged with cited evidence or explicitly accepted by a human naming the exact precondition exercised, then merges, sets Done, posts the summary, and files outside follow-ups. Three invariants are load-bearing: a missing/unparseable ledger BLOCKS (it is never read as "empty" — the original LIN-735 collapse; LIN-810 had relaxed this to absent-is-empty under an Approve, and LIN-3291 restored it: close-out names `review` to confirm empty or missing); green CI alone never discharges a ledger item (the item exists because CI cannot reach it); an empty ledger makes close-out a cheap no-op pass-through. Both paths move together — review/close-out templates in `lib/prompt-template-defs.js`, the trimmed Review rule (6→7) + new Close-out rule + Step-0/Step-3 routing in the meta-prompt — and the ledger stays INLINE per-template (NOT in the byte-identical `appendGroundingSections` post-pass, which would leak it into every template). The close-out body emits no literal "Linear" (it enters the LIN-177 byte-parity loop). Ledger items are **proportional to risk class** (LIN-898): an inherently-unprovable-before-merge claim (model/behavioural compliance, real-world recurrence) is a *hard gate item* only when the change touches runtime logic, a data path, security, or an external contract; for a low-risk, reversible change (prompt-text/docs/comment-only, no such surface) review records it as a *post-merge observation* that discharges via normal post-merge observation, and close-out cites that routing instead of demanding a pre-merge human sign-off. The fix is at review-*authoring* time (such a claim should never have been a hard gate item), NOT at discharge time — close-out still never accepts the reviewer's own "no action needed" self-assessment as a human sign-off, so the three floors above are untouched (missing ledger blocks, green CI never discharges, risky claims still need cited evidence or a named human precondition). The lane is keyed on the *risk surface*, never on LOC/t-shirt size/file type. **LIN-1579 widens that lane and adds a fourth load-bearing invariant — naming is its price.** Two named routes take a claim out of the hard-gate class: a claim unprovable *in principle* before merge discharges to a named **monitor** (a log/oplog entry, a metric, or a loudly-failing path — a thing that *fires*; **LIN-2917** struck the routed follow-up ticket from this list, since a ticket does not fire: it may be cited *beside* the monitor to record who holds the watch, never *instead* of it) *regardless of risk surface* — with the misfire guard now a required written line rather than prose: before an item takes the lane review writes one line naming why no check short of production could prove the claim, and close-out rejects a lane entry missing that line as undischarged, because a claim a test could have proven is an untested claim, not an unprovable one; and the low-risk lane now also covers a **runtime-logic** change that is genuinely reversible, meaning the reviewer names the rollback (the single commit to revert, or the exact env var/flag and its safe value), the rollback is complete (no migration, no data persisted in the new shape, no third party already consuming it), and it needs no coordinated release. Data-path, security, and external-contract surfaces are **not** widened into the rollback lane; an **unnamed** monitor or rollback does not get the lane; and the naming happens at review-*authoring* time, so close-out only ever cites a name someone else wrote — the change relaxes *how* an item discharges, never *who* authorizes the close (the LIN-550 → LIN-810 → LIN-811 → LIN-823 → LIN-1365 lineage against self-certification). **LIN-3033 adds who may *author* that discharge, a distinct question from who authorizes it:** close-out may write the change itself only when review named it with its exact content and it is trivially small (at most 2 files/3 hunks, no new or changed test/function/branch/condition/control flow — an update to an existing review-quoted literal/expected-string pin is allowed), covering every route close-out has used to author unreviewed content — a ledger item, a conditional-Approve caveat, a non-gating finding, a self-found sibling, a close-out-raised "do it here" ruling, or a merge-conflict resolution while landing the PR (a conflict-free merge or rebase stays ordinary mechanics, not authoring); anything else holds the merge and routes back to `implementation`, then `review`. LIN-1579 also closes bookkeeping on merge: verification possible on the landed commit is the merging session's last step rather than a separate pass, bounded by claims needing real-world *elapsed* time, which route to the named monitor instead of holding the task open. The posture is unconditional prose, not a flag — pre-launch, one workspace, `git revert` is the rollback; **LIN-282** ("move feature flags from user to workspace, apply to all prompt generation") is the tracked gap that would make it per-workspace, and the orchestrator briefing in `lib/prompts/autopilot-kickoff.js` restates the rule independently, so it moves with the templates. Class-check and ledger stay distinct: class = breadth (an outside sibling becomes a follow-up, an inside one a ledger item here instead), ledger = verification depth (what the deliverable rests on that CI can't prove → close-out gate items). `close-out` registers like any kind — `PROMPT_TEMPLATES` entry (with `aiHint`, so it is AI-recommendable), `COMPLETION_SIGNALS['close-out']`, and `VIRTUAL_PROMPTS.CLOSE_OUT`; all the derived surfaces (`getPromptLabels`, `DISPATCH_KINDS`, `deriveDispatchKind`, the meta-prompt action vocabulary) update automatically. **John's ruling on LIN-2825 adds a discharge rule inside the ledger, keyed on scope rather than risk.** `docs/papers/harbour/close-out-claims.md` measured that a review ledger item was discharged by filing a follow-up ticket for it, that the parent closed anyway, and that the filing was disproportionately the parent's own unfinished scope, never picked up. Review now marks every ledger item and every class-check sibling **inside** or **outside** the ticket's bounded classes (the classes LIN-1871 has research and plan bound, recorded in the issue description). **A class is defined by its kind, not by research's enumeration of it (LIN-3006, amending the original reading):** an **inside** item is part of solving this ticket's problem, its cause included wherever it lives (LIN-3291), or the same defect or idiom as a bounded class, whether or not research's list named it — the list is evidence of the class, not its edge — or a claim this ticket's own change depends on; it is this ticket's own scope, and close-out may discharge it only by cited evidence that it is done or by an explicit drop naming what is left and why, warranted only when finishing it is a change the team would need to hear about first (LIN-3291), not merely larger or inconvenient — filing a ticket for it is never a discharge, and close-out must not set Done over an undischarged inside item. An **outside** item is a different problem, never this ticket's cause, that no bounded class covers, and may be filed, provided the filing states the problem on its own terms; a `file` option is offered only for an outside item — an inside item's options are "do it here" or "drop it, with the reason". This is a different axis from the proportional risk lane above — a named monitor or rollback still discharges a claim that cannot be proven before merge at all, regardless of its inside/outside mark — and it does not touch the three LIN-550 floors (a missing ledger blocks, green CI never discharges, an empty ledger passes through). A plan breakdown's own phases/sessions are excluded from this rule; they are one task's children, not generated work. **LIN-3056 narrows when the conditional form itself applies:** the conditional-Approve wording is reserved for a ledger every item of which close-out can actually discharge within LIN-3033's trivial, review-named-edit bound; a ledger holding an **inside** item whose discharge requires authoring beyond that bound — a new or changed test, or a code change — gets **Request Changes** back to `implementation` directly, not a conditional Approve that close-out would only hold and bounce back anyway. This is a review-authoring-time wording change only: it does not touch LIN-3033's authoring bound or the ledger's inside/outside content rules.

The Surface Assessment necessity gate (LIN-192 origin, LIN-397 gate — research ends with an explicit verdict on whether the feature's shape *demands* a structural change, and plan turns only a *necessary* prerequisite refactor into a separate blocking subtask) lives in BOTH paths — the research template's Surface Assessment block + the plan template's conditional ratchet in `lib/prompt-template-defs.js`, and the Research-prompts + Plan-prompts quality rules in the meta-prompt. A `refactor required` verdict must pass two citation tests: the cause-or-consumer test (LIN-3291: show the refactor removes this task's confirmed cause, or cite the line in this task that calls the new seam — neither means speculation) and the who-pays test (every touched consumer is a beneficiary or a named-tax bystander — unjustified bystander tax means scope it down). A third verdict (`improvement noticed, not required`) gives noticed-but-not-demanded improvements a non-blocking home. Size is never a rejection criterion: a demanded refactor that doesn't fit the session is sequenced via the blocking subtask, not shrunk — effort is cheap for agents; speculation and bystander tax are not.

Provider capability-awareness (LIN-177 S4/S5) also spans BOTH paths via a single shared surface: `resolvePromptUi()` + `applyPromptCapabilities()` in `lib/prompt-formatters.js`. Call sites thread the active provider's `provider.ui` (`{write, comments, estimates, subtasks, displayName}`, from `getProviderForWorkspace(workspace)`) into `generatePrompt()`/`generateCustomPrompt()` (handwritten) and `buildMetaPrompt()`→`buildMetaPromptTemplate()` (meta). Provider capability is the hard floor; the `linearMcp` user flag is a soft preference within a writable provider. For Linear (every flag on, `displayName: 'Linear'`) every transform is a no-op, so Linear output is **byte-identical** — pinned by the parity test in `tests/unit/prompt-templates.test.js`. (`issue.source.provider` is not populated on canonical issues, so provider identity must come from the workspace, not the issue object. The proxy data-fetch in `routes/proxy.js` has been re-pointed onto the provider layer (LIN-308/309) and provider *selection* is now per-workspace via `getProviderForWorkspace` (LIN-581), the same resolution the render surfaces use.)

When changing prompt behavior, see **[docs/prompt-change-validation.md](docs/prompt-change-validation.md)** for the repeatable process (both-paths rule, overfitting guards, structural tests, and the offline A/B eval harness `scripts/eval-completeness-check.mjs`).
