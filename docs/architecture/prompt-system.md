Scope: the prompt system — one routing call, then code assembles the stage's prompt — and the rule for changing it. Moved from CLAUDE.md (LIN-2896); one path since LIN-3300.

### Prompt System (one path)

Every recommendation takes one path (LIN-3300):

- **Routing**: `lib/openrouter.js` → `getRecommendation()` / `getRecommendationStream()` sends the routing prompt, the **stage selector** (`buildRouterPrompt`, `lib/stage-router.js`), and reads the reply back with `routeStage`. The selector has four parts: the ticket as it sees it (`formatSelectorView`: title, state, labels, relations, the description with a long plan condensed, the newest three comments capped, the latest ruling and the latest person's comment wherever they sit, and the attachments); the facts code computes from the whole trail, as plain data (`assembleTrailFacts` / `formatTrailFactsBlock` in `lib/recommendation-facts.js`: the latest code review and its ledger, work or a close-out after it, the PRs linked, the latest person's comment and ruling, the plan-review verdicts by kind with the latest and whether a person commented or work landed since, and for a leaf the plan (when it lives in its parent's description, the facts name the parent), its session fit and whether a plan-review is due; under an approving review the ledger's open items read as left for close-out to discharge; for a node, the subtask counts and frontier); the task's **recent runs** from Harbour's dispatch record (`lib/recent-runs.js`: the newest five stage runs, oldest first, each its stage, finish time and outcome — done, failed, waiting on a person, running or queued), which every routed surface reads with `loadRecentRuns` and passes as `context.runs` (the UI's buffered GET and both stream paths in `routes/workspace-api.js`, and `computeRecommendation` in `routes/proxy.js`, which recommend-and-dispatch and the autopilot use), so a revision after a verdict or an agent's action after a person's comment is a fact rather than something read from prose; with runs, the comment-derived "an agent acted after it" reading is left out, and with none the selector decides from the ticket alone; the stages as they describe themselves (each template's `route`: when, when not, what it requires, plus the first sentence of its `STAGE_LEADS` entry as its purpose; `defer`'s from `RECOMMEND_META_ROUTES`); and the rules for choosing, written once, in order, each with its reason (`SELECTOR_RULES`). A rule says only what relates the stages (their order, and what only a rule can say, such as the plan-review cycle); when a stage applies is said once, in its own description. The latest person's comment decides the stage it names until the facts show an agent acted after it (its own note, landed work or a close-out). The model picks the stage and says why in one line; it writes no prompt. Code settles four routes itself, in order. The first is the **live-stage wait** (`liveWaitOf`, `lib/run-live-wait.js`, LIN-4392, moved to Runs by LIN-4459): while any stage run on the ticket is queued or running (a `stageRuns` fact, so `autopilot`, `custom`, wake and abort rows never count; waiting on a person, ended and aborted runs are not live), the hop sends no stage and asks no model; it answers wait, with `liveWait` (`{kind, id, dispatchedAt, outcome}`) naming the newest live run. It comes first because the bound below dispatches `blocked`, itself a stage, and because the selector, which sees live runs only as a `, started` hint, could otherwise pick a second stage beside one (the duplicate guard is keyed by issue and kind, looks back five minutes and runs only at the enqueue). It runs on every descent hop, so a parent with a live run stops the descent before its children are fetched. recommend-and-dispatch refuses a wait 409 `STAGE_IN_FLIGHT` naming the live dispatch to adopt; GET /recommend returns `prompt`, `recommendedAction` and `kind` null with `liveWait`; the task page's buffered GET carries `liveWait` and both its streams emit the refusal with no prompt. Only recommend-and-dispatch's `force: true` or a set `followUpTo` skips it (the `skipLiveWait` call option, on every hop), and the `kind` override never reaches a code route. A failed run read (`allRuns: null`) stands it aside. Age never ends a run: a wedged run holds its ticket, visibly, until it closes or is aborted. The wait is a read, not a claim, so two calls racing within milliseconds can both pass. The second is the **review loop bound**: a plan sent back three or more times since its latest Approve, with no person's comment and no landed work since the latest verdict, on a task that is not terminal, goes to `blocked` without a model call (`reviewLoopExhausted`, LIN-3309), unless it is converging: the latest two verdicts are Request Changes whose `Blocking findings: <n>` counts (the plan-review contract's line, read by `assemblePlanReviewFacts`) narrow or are both 1 (`reviewLoopConverging`, LIN-3651). A converging plan gets another round without a press, but five verdicts since the latest Approve (`REVIEW_LOOP_CEILING`) stop it whatever the counts; a missing count is today's behavior. It is structural (a planner and a reviewer who keep disagreeing must stop for a person), so no prompt states the count. Whether a plan was revised since a verdict is read from the trail by the model, not computed. Code settles a third route, the **blind read before close-out** (`blindReadStep`, `lib/recommendation-blind-read.js`, LIN-4438, piece 3 of LIN-4396): when the latest code review approves and some PR of the current landing (`landingPrUrls`) has no `## Blind read` naming it since that review, it sends `blind-read` (`closeOutDecision`'s `routesRead`, `lib/run-closeout-state.js`, LIN-4460, the one decision both close-out readiness lanes and the task page's box enforce too). It stands aside when work is reported after the review (the selector sends review first), on a Done ticket with a close-out on its landing or with no audit notes PR (a person closed it, and Harbour follows), and on a Canceled or Duplicate one; a close-out reported after the review does not stop it. Two ended reads since the review with none on record send `blocked`, only when runs are known. It reads whether a read is on record, never its verdict. Code settles a fourth route, the **look-first sequence** (`lookFirstStep`, `lib/recommendation-look-first.js`, LIN-4370): a fresh leaf with an `## As asked` block and no size of the move goes `survey-task`, then `survey-place`, then `scoping` (a gate-marked Periodical review goes to `scoping` alone, LIN-4398, since its docs-only PR gets no Surveys), each attempted once (a Survey's headed comment or any run of its kind counts; scoping's run or a size record does), with no model call. It applies only with no size record, plan or PR, no open blocker, a newest run not waiting on a person, and no person's comment holding it. **Restated invariant: code settles only the live-stage wait, the review loop bound, the blind read (an approving review with no read after it) and the look-first sequence (scoping alone on a gate-marked Periodical review); none reads a model's verdict, and a person's comment posted after work started outranks the look-first sequence until a later dispatched run.** "After work started" is after the earlier of the first run and the first Survey comment: comments before it are the filing and feed the Surveys; a later person's comment (`isPersonComment`) holds the route until a run *dispatched* after it exists (by `dispatchedAt`; a run merely ending later does not release it), while the selector's rule 1 acts on it. Headed comments, including a person's `## Size of the move (the person's call)` ruling, are not person comments and never hold; scoping reads them as rulings. An open `DECISION:` from a run that ended `done` does not hold it: the remaining look-first steps proceed once each and read that ruling (reading open questions here would need a new store read). Attempts come from the same single run read as the selector's five (`loadRecentRuns` returns both: up to 20 history rows, counted before non-stage rows are dropped, plus live rows), and a failed read stands the route aside. Once all three steps are attempted and none is live, the selector decides, so a scoping run that wrote no record falls through once and is never re-sent. Because the live-stage wait runs first, no step is sent while an earlier one is queued or running, so scoping never starts before survey-place's note exists. A wedged step is aborted (it then counts as attempted and the next step goes) or re-sent with the `kind` override. Both seams call one helper (`codeRoutedRecommendation`), so the streamed step and the step recommend-and-dispatch sends are the same, and the prompt trace records `codeRoute` (`live-wait` for a wait, which sends no step, `blocked` or `look-first`). The route reads whether a step happened, never what it said: the Surveys stay advice, not a gate, and keep `route: null`. Whatever wakes after scoping reads the ticket and its size record; no run's messages reach a prompt, so scoping's final report, which carries how, never reaches the builder (LIN-4369).
- **Assembly**: `lib/prompt-templates.js` → `generatePrompt()` builds the routed stage's prompt (`composeRoutedRecommendation`), byte for byte what a pinned stage gets. `defer` has no body; an action that names no stage is an invalid reply.

**A stage's traits are declared once, on its template** (LIN-4253). `route` says whether the selector offers the stage: `route: null` is never offered (retro, by hand only; the blind read, which code sends after an approving review; and the two Surveys, which the look-first sequence sends, except on a gate-marked Periodical review), and the stage selector, the router's refusal and the "Another step" list all read that declaration. `writes` says what the stage may write (`lib/stage-writes.js`, LIN-4251): `work` (the default: code, branches, PRs, comments, ticket updates); `none` (look-into, retro: report the findings in the session, write nothing); `one-comment` (context and the two Surveys: one comment on the ticket named in the task); `blind-comment` (the blind read, LIN-4437: one comment, and its preamble names no ticket read, only where the comment goes); `ticket-fields` (triage: this ticket's labels, priority, state and project, and a comment; no code, no PRs, no new tickets). Each value has its mandate and closing in the preamble's `WRITES_BLOCK`, and every value other than `work` drops the "update the workspace as you work" hint (`blind-comment` replaces the hints whole). `dispatch-entrance` and the feedback entrances resolve `writes` through `stageWrites(kind)` (`lib/prompt-templates.js`), and a follow-up that names a stage gets that stage's block; the preamble keeps no stage names. A template missing either trait fails `tests/unit/lin-4253-stage-traits.test.js`. `writes` is not `readOnly`: triage writes ticket fields. A stage is a reading pass exactly when its `writes` is `none`, `one-comment` or `blind-comment`, in both directions (the blind read has its own reading-pass line, which names no ticket). plan-review is the known leftover: it writes one comment and is read-only in its body, but still declares `work` (LIN-4251 scoped it out).

So prompt behavior (feature flags, workflow instructions, context formatting, a stage's rules) is changed in one place, the stage templates (`lib/prompt-template-defs.js`, `lib/prompt-formatters.js`, `lib/prompt-contract.js`, `lib/prompts/stage-intent.js`); routing behavior is changed in `lib/stage-router.js` and the facts it reads. Before LIN-3300 a second, model-written path (the meta-prompt template, and an experimental brief writer that rewrote a stage's Goal lead) had to mirror every rule; both were deleted, not switched off.

**Rules assembled by code.** A template body is its title, `## Workflow`, facts block, a `## Goal` that is only the stage's lead (its intent: what the work is for, what good looks like, its limits; `STAGE_LEADS` in `lib/prompt-template-defs.js`, the one intent source per stage, LIN-3299) and a `## Process` holding the stage's rules with their reasons, then sometimes `## If Blocked`. `generatePrompt()` is the template body plus `finishStagePrompt(body, kind, …)` (`lib/prompt-templates.js`), which first puts the stage's `## Scope and Authority` after the Goal's lead (`withStageIntent`, `lib/prompts/stage-intent.js`: LIN-3291's cause-is-in-scope and authority lines, one for stages that choose or build, one for stages that judge or investigate and one for reading passes, plus any stage line its process does not already state), then appends everything code adds after a body, in order: the **stage contract**, grounding, attachments, the code-review sections and the capability pass. The contract (`formatStageContract`, `lib/prompt-contract.js`) carries every format a later step parses, each tested against its reader: the plan's `## Implementation Plan` heading, session-fit phrase and `plan-review due:` line; plan-review's `### Plan Review Verdict` header and verdict line; implementation's PR URL; review's title, head sha, CI line, ledger and verdict forms; close-out's title and the literals its prune keeps. A read-only tracker gets none, and no template asks for the same formats, so each is said once. A change to a machine-read format is a contract change: edit `CONTRACT_LINES` and its reader test (`tests/unit/prompt-contract.test.js`), not prose.

Every surface that hands out a stage prompt takes this path. Routed ones (the UI's Recommend stream and buffered GET, proxy GET recommend, recommend-and-dispatch, and the autopilot and lanes that call them) make one routing call per descent hop with the workspace's `recommend` model; pinned ones, where the stage is chosen up front (the UI's stage buttons, `recommend?kind=`, recommend-and-dispatch with `kind`, the proxy template read `GET …/prompt/:templateKey`), call `generatePrompt()` and make no model call. The stream sends the routing reasoning live and the finished prompt as one delta (a `## Prompt` section a model writes anyway is dropped). A client hang-up aborts the routing call but never an enqueue that has started; it is recorded as 499, never as an AI outage. The routing prompt is pinned byte for byte by `tests/fixtures/stage-router-prompts/` (real tickets rendered through `buildSelectorArgs`) and frozen with the templates (`tests/unit/prompt-size-budget.test.js`). A surface grows only with its reason recorded beside the ceiling it raises (the ticket, the bytes, and why the lesson cannot be code or a test); a shrink needs no edit. A routing change is a change to a stage's `route`, a selector rule or a fact; a rule is added only with its reason, and a rule in code only where it is structural, as the loop bound and the look-first sequence are.

**Deterministic grounding sections are a single shared post-pass (LIN-435), not duplicated prose.** Five notes — the staleness check, terminal-state note, all-subtasks-complete note, bug-already-investigated note and the area notes pointer — are appended by `appendGroundingSections(prompt, issue, context, kind)` (`lib/prompt-formatters.js`), which `finishStagePrompt` runs as a post-pass over the rendered body, so the rules execute once: the routing prompt no longer re-types these rules as prose and they cannot drift. The notes are chosen per stage, not appended to every template (LIN-3296): `GROUNDING_BY_KIND`, next to `appendGroundingSections`, lists which notes each template kind gets (a routed recommendation maps its action through `deriveDispatchKind` to the same key), so a look-back (`retro`, `retrospective-audit`) or read-only stage is never told to close out or implement the fix, `triage` gets none, and the bug-investigated note goes to `implementation` only. The area notes pointer (LIN-4371) goes to the seven stages that read or change code in an area (`implementation`, `bug`, `plan`, `research`, `design`, `spike`, `review`): one fixed line telling the agent to read `docs/areas/` for each area the work touches (`docs/areas/README.md` owns the notes' format). It names no repository, so it serves every repository that keeps `docs/areas/`; scoping gets its own wording (`formatScopingAreaNotesPointer`, LIN-4346): its size record takes no fifth line and it posts no comment, so it cites a note entry in its final message. The Survey stages get none: survey-place reads no reports on the codebase's shape, and those reports feed the notes. A kind not in the table (custom) keeps the first four notes. Skipped for `defer` replies (no body, the no-body cost contract). The staleness `--since` date is injected deterministically from `issue.createdAt`, never a placeholder. Pinned by the grounding tests in `tests/unit/prompt-templates.test.js`.

The ticket staleness check (re-ground against current code: list referenced files/symbols, `git log --since=<createdAt>`, re-read source at HEAD before trusting the ticket) is `formatStalenessCheck()`, appended via the shared post-pass above. Its hypothesis sentence covers any solution or limit the ticket proposes as well as its account of the code (LIN-3299: a research run had adopted a ticket's prescribed "leave this file unchanged" as its own limit).

The plan-fidelity check (LIN-698 — the *symmetric* counterpart of the staleness check, one stage earlier in the pipeline: the staleness check distrusts the ticket's claims about the **code** and re-grounds them against HEAD; this distrusts the plan's claims about the **research** and re-grounds them against the research/exploration notes + comment thread the plan was distilled from — surface, don't silently absorb, anything the plan dropped or contradicted, and on conflict the research's reasoning wins) is `formatPlanFidelityCheck()` in `lib/prompt-formatters.js`. It is **implementation-specific**, so unlike the four universal grounding rules it is **NOT** routed through `appendGroundingSections()` (that seam is shared by all templates; plan-fidelity would leak everywhere) — instead the implementation template calls it inline, next to the adjacent refactor/behavior-preservation equivalence check (don't trust a "refactor"/"behavior-preserving" label, enumerate and verify the old behaviors, ideally via a characterization test). Pinned by the LIN-698 tests in `tests/unit/prompt-templates.test.js`.

The terminal-state *body note* (LIN-353 — a Done/Canceled/Duplicate task with no open children is not redone as if unstarted) is `formatTerminalStateNote()`, also via the shared post-pass; it and the all-subtasks-complete note ask what the stage they reach does (LIN-3292): review checks the work and puts what is missing in its verdict, close-out lands it and sends what is missing back to implementation, and any other stage routing sent a finished task to does its own part for what is still missing, at its cause (plan-review and the stages that build nothing are not told to fix). Neither tells any stage to file what is missing as a follow-up. Its *routing* counterpart — the selector's landed-work rule (rule 2), which reads the trail facts — is in `lib/stage-router.js`, because action selection is the router's alone. (The deterministic descent guard that refuses defers into terminal nodes is separate, in `lib/recommend-recurse.js`.)

The bug-already-investigated *body note* (LIN-366 — a `bug`-labelled task with prior investigation in its comments advances to the fix instead of re-recommending investigation, because the `bug` label alone is not a reason to re-investigate) is `formatBugInvestigatedNote()`, via the shared post-pass; its *routing* counterpart — the selector's bug rule (rule 5) and the `bug` stage's own "not when" — is in `lib/stage-router.js` and `lib/prompt-template-defs.js` for action selection. It is a soft signal (no deterministic "investigated" marker exists; findings live in free-form comments), gated on `bug` label + ≥1 comment.

The class check (LIN-313 — "widen the model, don't patch the witness": once a bug's root cause is in hand, or before a review approves the close, ask whether the work is an isolated instance or one of a class with unhandled siblings) is woven into the bug template's investigation steps and the review template's "Isolated, or One of a Class?" section in `lib/prompt-template-defs.js`. Since LIN-3291 the proposed fix is at the cause: a found class is named and the fix reaches its instances at their shared cause, refactoring where that simplifies the code, and a genuinely isolated result is explicitly valid. It is the execution-altitude sibling of the plan template's completeness standard (LIN-295; its wording is now the behaviour-and-places rule, LIN-4021).

**The blind read is the one read of what a change left at its edges (LIN-4438, piece 3 of LIN-4396; it retired review's edges read, LIN-4374).** Review keeps one sentence of it: the builder's `### Leftovers` comment (the leftover step's answer, `lib/dispatch-leftover.js`; heading `LEFTOVERS_HEADING` in `lib/prompts/leftover-words.js`) names on its `Retires:` line the waiting entry the build settled (a shape the proxy checks, LIN-4414), and review checks that this diff removes it, which the blind reader cannot, since it never sees the leftovers. The read itself is the `blind-read` stage, sent by code between an approving review and close-out (the route above), blind to the ask, the plan and the leftovers. Close-out takes the rest of the hand-off: Workflow step 1 and Make the Fixes read the `## Blind read` comment, fix its fix-sized inside finds on the PR branch and list them with their commits (they are not re-read), and send its other finds through Follow-up Triage, which renders `LEFTOVER_RULE` and `CONSEQUENCE_TEST` and also takes the builder's lines marked for close-out (`FOR_CLOSE_OUT`, the leftover prompt's spelling of that mark) through the same gate. Close-out stays the only filer of tickets. Its not-ready sentence holds the gate for the lanes the dispatch guard does not see: a PR not linked on the task is linked in a plain comment of its own (no heading, a first line naming the PR that is never a close-out report or an agent note), then `review`; no blind read since the review naming the PR, then `blind-read`. Readiness: the stop-at-PR state (`deriveCloseOutState`, reason `blind-read-missing`), the task page's box (`buildRunEvidence`) and both dispatch-guard lanes (`closeOutNotReady`) render `closeOutDecision` over the same landing (LIN-4460). `retrospective-audit` and `retro` are unchanged.

The behaviour-and-places rule (LIN-4021, replacing the class-not-member rule of LIN-1871 and LIN-1873) lives in the research, plan, and plan-review templates in `lib/prompt-template-defs.js`, in the wording agreed in `docs/reviews/stage-prompts-2026-10-29/proposed-prompts.md`. The standard is one sentence in both prompts: a change is finished when the behaviour is right everywhere it lives, not just where the ticket pointed, and the author says how they know they found every place. Research names the behaviour, its places and how it bounded them; a reproducible query whose output is the enumeration is one way to bound it, and the strongest where it applies. The plan builds on research's list and re-checks what it relies on: every member ends up in or out of its scope, and the list is evidence for the plan, not a contract. Plan-review judges the reasoning: an unlisted place inside a correct description is a note, while a place outside the description makes the description the finding, corrected whole. Only what would make the build go wrong blocks; everything else is a note for the builder.

The plan's research seam (LIN-3202, now the plan template's Process in `lib/prompt-template-defs.js`) asks that a plan be an addition to the research, not a copy of it. Where research ran, the plan builds on it and cites what it relies on (by comment, file:line or sha) rather than restating it, and the claims are the plan's own. Everything research found that the change must handle is in the plan or set aside with a reason, and where the plan disagrees with research it says why. Citations must resolve for a reader, including a breakdown child (LIN-3049) that receives only a copied plan slice and not the parent's research comments. Where there is no prior research the plan stands alone, with no citations to manufacture.

**What was asked is a fixed block every step reads (LIN-4345: pieces LIN-4351, LIN-4352, LIN-4353).** A ticket's description opens with an `## As asked` block: the description as filed, byte for byte, between the `## As asked` heading and the end line `*End of what was asked. Steps write below this line; nothing above it changes.*` (`lib/as-asked.js` owns both markers). Code seals it where a ticket starts (the proxy, session and feedback creates, and a ticket's true first dispatch in `lib/dispatch-factory.js`, through `lib/as-asked-seal.js`), and only there. The proxy guards it: a description write through the agent lane (PATCH, `description/replace`, `description/append`) that would change, drop or add the block is refused 422 `AS_ASKED_IMMUTABLE`, naming the first line that differs; the session lane and edits in the tracker stay open, so the person can still edit their own words. Code that reads state from a description (the plan heading, session fit, the `plan-review due:` line) uses `readFact`: below the block wins, and the block is read only when the text below lacks that fact. The brief composer (`composeBrief`, `lib/as-asked.js`) quotes the block verbatim ahead of the model's four sections, so the words never pass through a model (a subtask whose parent has a block gets the parent's words too, under `## As asked on the parent`: John's whose-words ruling, 7 Nov, since a breakdown child's own block holds the agent's slice of the plan); the preamble's brief hint says so once for every stage. Stage prompts point at the block rather than copy it (the not-a-copy rule): plan and plan-review judge against it, review starts from it before the plan, review accounts for each sentence of the block in order, none skipped or cut short, saying where the work meets it (LIN-4345); plan-review says in one line how the plan meets it; close-out cites review's account. Deciding stages (the `DECIDE` scope line: research, scoping, design, spike, plan, breakdown, implementation, blocked) name each cut to the block, quoting the words reduced, and raise the cuts as one ruling, a `DECISION:` before `BLOCKED:`, so Harbour records it; the rule lives once, in `lib/prompts/stage-intent.js`. Close-out prunes only below the block, through `POST …/description/below`, which keeps the live block as stored; a description with no block is not pruned.

**The file-pointer pilot (LIN-3200, menu M10) is a seam DOWNSTREAM of the prompt, not a template edit.** A short pointer is PREPENDED at dispatch time (lib/dispatch-factory.js step 7.6) to the **implementation** prompt only, on every second eligible implementation dispatch chosen deterministically from the live ordinal. It is built from two inputs already in the record: the plan's named paths, parsed from the issue description's `## Implementation Plan` block (heading matched by PREFIX, last match wins, because real headings carry suffixes), and the files edited in earlier PRs on the ticket, read from GitHub at dispatch time (lib/github-pr-files.js) because only the PR URL is recorded. The pointer never carries commit shas and no literal tracker name. Reviewers are excluded by EFFECTIVE KIND: the step's gate is `effectiveKind === 'implementation'` (plus fresh, issue-scoped, non-abort, non-follow-up), so review/plan-review/close-out/plan/research/triage/autopilot/custom output is byte-identical, and reviewer independence — a reviewer steered to the implementer's files may stop looking elsewhere — is preserved. **Preview and copied prompts are the control form**: they enqueue nothing, decide no arm, and are untouched. The arm rule is recomputable from existing row fields (`kind`, `followUpTo`, `abort`, `issueIdentifier`, `dispatchedAt`, `resolvedAt`) and adds NO row field; `addItem`'s argument is byte-identical in every arm except a delivered pointer. The arm is the ordinal parity over the lifetime retained eligible set: even ⇒ pointer, odd ⇒ control (lib/file-pointer.js `selectPilotArm`). Its limits are named, not claimed away: **R1** a count/read failure is fail-open (untouched prompt, unflaggable from rows); **R2** a store hop that outlasts `HOP_ALLOWANCE_MS`, and its write-side twin the insert lag from `addItem`'s `dispatchedAt` stamp to its visible `insertOne` above `RACE_SUSPECT_WINDOW_MS − COUNT_TIMEOUT_MS`; **R3** a swallowed archive failure (both `Error archiving dispatch item:` from `_archiveItem` and `Error archiving expired items:` from `cleanup()`'s skipped archive loop) removes a row from both collections; **R4** clock skew above `SKEW_SLACK_MS`. The read (scripts/file-pointer-read.mjs) excludes race-suspect rows from the primary comparison in both arms. The recompute depends on **LIN-3163's lifetime history retention** (`c572a681`); if retention is ever bounded again the recompute is invalid after the first trimmed row and the comparison restarts.

 **Every prompt-template change — not just this one — lands with a row in `scripts/prompt-template-change-log.md`** (John's 2026-08-04 ruling on LIN-1661; definitional home LIN-1662): date, commit sha, ticket, the surface changed (`template` or `router`; rows before LIN-3300 say `handwritten`/`meta`), a one-line behavioural description, and an expected direction (`up`/`down`/`unknown`) recorded BEFORE the follow-on-ratio read, so a direction cannot be rationalised after the number arrives. The follow-on-ratio measurement (`scripts/follow-on-ratio.mjs`) is protected by RECORDING changes, never by freezing them — the 2026-08-04 ruling withdrew the freeze outright ("the read stands, the abstinence does not"), and John's 2026-09-04 ruling confirmed the later Flight Companion extension defers only the read. When appending, use the re-runnable query recorded in the change log itself: a bare `git log --since=<date>` is git *approxidate* and silently drops commits from earlier in that day.

The mutation-check directive (LIN-2274 — before approving a close, a reviewer must mutation-check the load-bearing new/changed tests for at least the deliverable's own claimed behavior: delete or comment out the code path each one claims to cover, confirm it goes red, then restore it — "the test exists and asserts something" is not proof it asserts the *right* thing) lives in the review template's `### Test Quality Check` section (a guideline bullet, immediately before `### Review Checklist`; since LIN-3293 the checklist no longer repeats it), in `lib/prompt-template-defs.js`. It is the review-side counterpart of LIN-2219's acceptance-witness discipline one stage earlier in the pipeline (implementation template guideline 6): LIN-2219 asks the *implementer* to mutation-check their own new tests before trusting them; LIN-2274 asks the *reviewer* to independently mutation-check *load-bearing* tests before approving the close — closing the gap where "the test exists and asserts something" was accepted as proof it asserts the right thing. Pinned by the LIN-2303 tests in `tests/unit/prompt-templates.test.js`.

Two reviewer rules from LIN-3615 sit beside it: plan-review's Check 5 treats converting a source-text or location pin the ticket permits as no loosening once the behaviour replacement lands first and fails with the guard removed (a ticket naming security guards keeps every check), and review's Test Quality Check takes behaviour, not a test that reads source for where code sits, as the witness for a move.

The review→close-out split (LIN-550) makes close-out a first-class step distinct from `review`, so the irreversible finish has an owner and a gate. `review` is now **write-only**: it appends a `### What CI Did Not Prove` ledger (the "Not-Proven-by-CI" handoff — every claim the deliverable depends on that green CI does not exercise) to its summary comment and issues a verdict that is **conditional** when the ledger is non-empty (`Approve — conditional on close-out discharging the ledger`, never a bare Approve); it does NOT merge, set Done, or file tickets (LIN-3293: filing has one owner, so review names each outside find's home under the consequence test (LIN-4401), and close-out files the gate's tickets so a reader with no access to the ticket can act on it, after its existing-ticket check). The new `close-out` template (`category: UNIVERSAL`, key `close-out`) **consumes** that ledger and finishes the work: it settles each ledger item with cited evidence (or a human's acceptance naming the exact precondition exercised), merges, does the post-deploy steps once the deploy has landed, sets Done, posts the summary, and files the gate's tickets, writing each other outside find as a note entry. Three invariants are load-bearing: a missing/unparseable ledger BLOCKS (it is never read as "empty" — the original LIN-735 collapse; LIN-810 had relaxed this to absent-is-empty under an Approve, and LIN-3291 restored it: close-out names `review` to confirm empty or missing); green CI alone never discharges a ledger item (the item exists because CI cannot reach it); an empty ledger makes close-out a cheap no-op pass-through. The review/close-out templates live in `lib/prompt-template-defs.js` and their routing in the selector's landed-work rule (`lib/stage-router.js`), and the ledger stays INLINE per-template (NOT in the byte-identical `appendGroundingSections` post-pass, which would leak it into every template). The close-out body emits no literal "Linear" (it enters the LIN-177 byte-parity loop). Ledger items are **proportional to risk class** (LIN-898): an inherently-unprovable-before-merge claim (model/behavioural compliance, real-world recurrence) is a *hard gate item* only when the change touches runtime logic, a data path, security, or an external contract; for a low-risk, reversible change (prompt-text/docs/comment-only, no such surface) review records it as a *post-merge observation* that discharges via normal post-merge observation, and close-out cites that routing instead of demanding a pre-merge human sign-off. The fix is at review-*authoring* time (such a claim should never have been a hard gate item), NOT at discharge time — close-out still never accepts the reviewer's own "no action needed" self-assessment as a human sign-off, so the three floors above are untouched (missing ledger blocks, green CI never discharges, risky claims still need cited evidence or a named human precondition). The lane is keyed on the *risk surface*, never on LOC/t-shirt size/file type. **LIN-1579 widens that lane and adds a fourth load-bearing invariant — naming is its price.** Two named routes take a claim out of the hard-gate class: a claim unprovable *in principle* before merge discharges to a named **monitor** (a log/oplog entry, a metric, or a loudly-failing path — a thing that *fires*; **LIN-2917** struck the routed follow-up ticket from this list, since a ticket does not fire: it may be cited *beside* the monitor to record who holds the watch, never *instead* of it) *regardless of risk surface* — with the misfire guard now a required written line rather than prose: before an item takes the lane review writes one line naming why no check short of production could prove the claim, and close-out rejects a lane entry missing that line as undischarged, because a claim a test could have proven is an untested claim, not an unprovable one; and the low-risk lane now also covers a **runtime-logic** change that is genuinely reversible, meaning the reviewer names the rollback (the single commit to revert, or the exact env var/flag and its safe value), the rollback is complete (no migration, no data persisted in the new shape, no third party already consuming it), and it needs no coordinated release. Data-path, security, and external-contract surfaces are **not** widened into the rollback lane; an **unnamed** monitor or rollback does not get the lane; and the naming happens at review-*authoring* time, so close-out only ever cites a name someone else wrote — the change relaxes *how* an item discharges, never *who* authorizes the close (the LIN-550 → LIN-810 → LIN-811 → LIN-823 → LIN-1365 lineage against self-certification). **LIN-3326 replaced LIN-3033's authoring bound** (close-out had authored only a review-quoted edit of at most 2 files/3 hunks, never a merge-conflict resolution or a "do it here" ruling, so on LIN-3325 an approved, green task could not be finished by any agent): close-out makes the fixes review asked for itself, however many files they touch, and resolves a conflict landing needs, as long as each stays the size of a fix; a new design or new behaviour goes back to `review`. It lists each change in its summary with its commit, because nobody reviews it after the approval, and re-establishes CI on the new head before the merge. **LIN-3326 also retired the risk-surface hard gate:** a step that can only run once the change is live (a live check, a data clean-up) is recorded by review as a post-deploy step and done by close-out after the merge, once the deploy has landed (Harbour's deployed commit is in its page footer, `lib/deploy-info.js`), never held as a condition on the merge. **LIN-3614 bounded what holds the close, and LIN-3903 (John's 12 Oct standing ruling) retired its asked/unasked split:** the task stays open only if the deploy has not landed, a post-deploy step ran and failed, or a post-deploy step that is not a check (a data clean-up, a migration) is beyond close-out's access; once the deploy has landed, a post-deploy check close-out cannot run never holds the close, however the ticket or review names it. It is recorded as not run (what, why, and who can run it) on the ticket and in the PR, listed for the operator, and the task closes with no ruling; a product question is not a check and still gets one. No monitor settles it, since LIN-3559 shows a named monitor may not fire. Review no longer filters the post-deploy route by what the ticket asks for or close-out can run; a claim only a human can verify is a ledger item marked not run, with why. LIN-1579 also closes bookkeeping on merge: verification possible on the landed commit is the merging session's last step rather than a separate pass, bounded by claims needing real-world *elapsed* time, which route to the named monitor instead of holding the task open. The posture is unconditional prose, not a flag — pre-launch, one workspace, `git revert` is the rollback; **LIN-282** ("move feature flags from user to workspace, apply to all prompt generation") is the tracked gap that would make it per-workspace, and the orchestrator briefing in `lib/prompts/autopilot-kickoff.js` restates the rule independently, so it moves with the templates. Class-check and ledger stay distinct: class = breadth (an outside sibling becomes a note entry, or a ticket if the consequence test sends it there; an inside one a ledger item here instead), ledger = verification depth (what the deliverable rests on that CI can't prove → close-out gate items). `close-out` registers like any kind — `PROMPT_TEMPLATES` entry (with `route`, so the selector offers it), `COMPLETION_SIGNALS['close-out']`, and `VIRTUAL_PROMPTS.CLOSE_OUT`; all the derived surfaces (`getPromptLabels`, `DISPATCH_KINDS`, `deriveDispatchKind`, the router's action vocabulary) update automatically. **John's ruling on LIN-2825 adds a discharge rule inside the ledger, keyed on scope rather than risk.** `docs/papers/harbour/close-out-claims.md` measured that a review ledger item was discharged by filing a follow-up ticket for it, that the parent closed anyway, and that the filing was disproportionately the parent's own unfinished scope, never picked up. Review now marks every ledger item and every class-check sibling **inside** or **outside** the ticket's bounded classes (the classes LIN-1871 has research and plan bound, recorded in the issue description). **A class is defined by its kind, not by research's enumeration of it (LIN-3006, amending the original reading):** an **inside** item is part of solving this ticket's problem, its cause included wherever it lives (LIN-3291), or the same defect or idiom as a bounded class, whether or not research's list named it — the list is evidence of the class, not its edge — or a claim this ticket's own change depends on; it is this ticket's own scope, and close-out may discharge it only by cited evidence that it is done or by an explicit drop naming what is left and why, warranted only when finishing it is a change the team would need to hear about first (LIN-3291), not merely larger or inconvenient — filing a ticket for it is never a discharge, and close-out must not set Done over an undischarged inside item (a post-deploy check close-out cannot run once the deploy has landed is the one exception: it is recorded as not run, LIN-3614/LIN-3903). An **outside** item is a different problem, never this ticket's cause, that no bounded class covers, and goes to its home under the consequence test (LIN-4401: a ticket only if it breaks, blocks or touches safety, stating the problem on its own terms; otherwise a note entry in its area); a `file` option is offered only for an outside item the test sends to a ticket — an inside item's options are "do it here" or "drop it, with the reason". This is a different axis from the proportional risk lane above — a named monitor or rollback still discharges a claim that cannot be proven before merge at all, regardless of its inside/outside mark — and it does not touch the three LIN-550 floors (a missing ledger blocks, green CI never discharges, an empty ledger passes through). A plan breakdown's own phases/sessions are excluded from this rule; they are one task's children, not generated work. **LIN-3056 had reserved the conditional form for a ledger close-out could settle within LIN-3033's bound;** with the bound gone (LIN-3326), a non-empty ledger or a named fix gets `Approve — conditional on close-out discharging the ledger`, and **Request Changes** is for work that still needs a new design or new behaviour.

The Surface Assessment necessity gate (LIN-192 origin, LIN-397 gate — research ends with an explicit verdict on whether the feature's shape *demands* a structural change, and plan turns only a *necessary* prerequisite refactor into a separate blocking subtask) lives in the research template's Surface Assessment block + the plan template's conditional ratchet in `lib/prompt-template-defs.js`. A `refactor required` verdict must pass two citation tests: the cause-or-consumer test (LIN-3291: show the refactor removes this task's confirmed cause, or cite the line in this task that calls the new seam — neither means speculation) and the who-pays test (every touched consumer is a beneficiary or a named-tax bystander — unjustified bystander tax means scope it down). A third verdict (`improvement noticed, not required`) gives noticed-but-not-demanded improvements a non-blocking home. Size is never a rejection criterion: a demanded refactor that doesn't fit the session is sequenced via the blocking subtask, not shrunk — effort is cheap for agents; speculation and bystander tax are not.
