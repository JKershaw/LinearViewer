**Who can create a local workspace, and where the door is.**
- Anyone, signed in or not: the route checks nothing before writing (`routes/workspace.js:41-106`). The only limit is ten workspaces per session (`lib/workspace.js:70`, `:254`).
- A signed-out visitor sees the button "+ local workspace" only in the top bar of the previews `/swipe`, `/swim` and `/ship` (`lib/components/navbar.js:115-117`), which `/` links to in its footer (`lib/components/footer.js:120-141`). The agent guide sends people that way: "open /swipe, choose + local workspace" (`docs/agent-onboarding.md:52-60`).
- A signed-in person sees it in the workspace switcher (`lib/components/navbar.js:511-522`), on the account home `/account` (`lib/render-account-home.js:70`) and on the Workspace Not Found page (`lib/render-pages.js:911`).
- The landing page's provider strip does list "Local: a store kept here, for work with no tracker behind it" (`lib/providers/local/index.js:611-613`; `lib/render-landing.js:390-394`), with no door beside it.

**How it relates to accounts and email sign-in.**
- Signed out: a new account is minted whose only identity is `('local', <urlKey>)`; there is no human credential on it (`routes/workspace.js:85-90`; `lib/account-session.js:171-175`).
- Signed in (by email or a tracker): the workspace is bound to the current account, which becomes its owner (`lib/account-session.js:167-170`, `:234-235`).
- Email sign-in lands a person with no workspaces on `/account`, which carries the "Create a local workspace" form (`routes/email-auth.js:687`; `lib/render-account-home.js:63-70`). So email then local is a coded route.
- Where email sending is configured, a fresh workspace's first page load is redirected once to a skippable "add your email" step (`routes/email-auth.js:356-389`; `lib/email-availability.js:98-105`).
- **A local workspace lives in the browser session that made it.** Workspaces are read from `req.session.workspaces` (`server.js:2601-2614`). Email sign-in carries over only what the session already holds (`routes/email-auth.js:641-654`). The account page says so: "Workspaces don't follow you to a new device yet: reconnect a source here" (`lib/render-account-home.js:26`). For a tracker, reconnecting rejoins the same workspace; for local, `POST /workspace/new` always mints a new key (`routes/workspace.js:45-57`), and the one reader of an account's workspace list is the account-merge code (`lib/account-store.js:264`). So after logout, a lost cookie or 30 idle days (`lib/session-options.js:14`), I found no way back to the same local workspace; its rows stay in `local-issues` (inferred from the absence of any restoring code).
- The same session row is what the agent API uses: a proxy token resolves the workspace by finding its owner's live session (`server.js:2648-2650`, `:2975`), where a local workspace's "token" is its own key with a never-expiring sentinel (`routes/workspace.js:72-75`; `lib/workspace-token-resolver.js:72-76`). When the owner's session row is gone the answer is `owner_signed_out` (`server.js:2676-2678`). (Inferred for local; the mechanism is provider-neutral.)

**Can a local workspace connect a GitHub repository?**

A local workspace holding a GitHub binding is exercised in `tests/e2e/detail-nonactive-binding.spec.js:198`.
