# Area read: the paired readability kit (LIN-4453, piece 0)

A frozen measurement kit. It asks fresh readers how readable an area is, once for each area in the same window: Runs & dispatch, which the work changes, and the untouched control `front-end-pages`. The same kit runs again after the last piece of LIN-4447 (LIN-4462), and the after-read verifies this file by blob SHA. Do not edit this file once the baseline reports cite it. A change is a new kit with a new name.

It retires nothing. It adds no code. Its reader prompt is [area-read-reader-prompt.md](area-read-reader-prompt.md). Its shared rules are the ones the `blind-read` pilot set (`docs/plans/survey/blind-read-prompt.md`); they are copied into this kit, so it stands on its own and the after-read does not depend on the template staying the same.

## Counting basis

A file belongs to an area by the registry's first match: take the first area in `docs/areas/areas.json` with a pattern that matches the path. The scope is the code-shape scope, the one `scripts/code-shape` uses: `.js`, `.mjs` and `.cjs` files, excluding `node_modules`, vendored code, `.min.js`, test directories, `*.test.*`, `*.spec.*` and pinned replay copies.

- Runs & dispatch: 115 files, 2,261,263 bytes. The ticket's 116 adds `lib/runner-kit/contract.json`, which is JSON, not code, and falls outside the code scope.
- Front end: server-rendered pages: 92 files, 1,125,225 bytes.

The raw match (every pattern that could claim a file, before first match) puts `lib/dispatch-tokens.js` in Runs as well. First match sends it to Agent API, so it is not in the sample universe. The sample uses first match only.

## The sampling rule

For each area, at the base commit:

1. Take the code-scope files whose first-matching area is that area.
2. Key each path: `sha256("lin-4453-area-read|" + path)`, as lowercase hex.
3. Sort the files by key (plain string order). Take the first N = 14.

**Why this rule.** A stable hash keeps a picked file picked while the area changes, and a new file enters only if its key ranks in the first 14 among the area's files. A "largest N" rule would pick `lib/dispatch-store.js` and `lib/dispatch-entrance.js` first, which the plan leaves mostly alone. A "first N" rule moves as files are added or removed. The count is the same for both areas, as the ask requires.

**Why N = 14.** An equal count cannot match bytes in general, since the two areas' files differ in size on average (about 19.7 KB against about 12.2 KB). Among the counts tried, 13 to 16, N = 14 gives the closest byte totals at the base commit: 199,552 bytes for Runs and 206,530 for the control, a 3.4% gap. N = 13 gave 187,414 and 200,359; N = 15 gave 265,499 and 235,264; N = 16 gave 269,657 and 238,101. N = 12 gave 141,499 and 193,478. N is fixed now and is not changed in later reads.

**After the work, the same rule.** The after-read re-applies the rule to the area as it then stands, with N = 14. A file added to an area enters if its key ranks in the first 14; a file removed drops out, and the next key takes its place. Each report records the manifest it used. Files in both manifests are the paired set, and the paired set is reported as a secondary figure. Verdicts use the full sample.

**Reproduce the list.** Run from the repository root at the base commit. Pass the base commit, the area slug and N. The snippet prints each picked path with its byte size, then a TOTAL line:

```sh
node --input-type=module - 4b5001ddf runs-and-dispatch 14 <<'EOF'
import { execFileSync } from 'node:child_process';
import { createHash } from 'node:crypto';
const [base, slug, nArg] = process.argv.slice(2);
const N = Number(nArg);
const git = (...a) => execFileSync('git', a, { maxBuffer: 1 << 28 }).toString();
const areas = JSON.parse(git('show', `${base}:docs/areas/areas.json`)).areas;
const inScope = (p) => /\.(js|mjs|cjs)$/.test(p) && !/(^|\/)node_modules\/|(^|\/)vendor(ed)?\/|\.min\.js$|(^|\/)(tests?|__tests__)\/|\.(test|spec)\.|^experiments\/[^/]+\/replay\/(pinned|work)\//.test(p);
const firstArea = (p) => areas.find((a) => a.match.some((m) => new RegExp(m).test(p)))?.slug ?? null;
const files = git('ls-tree', '-r', '-l', '-z', base).split('\0').filter(Boolean)
  .map((r) => { const t = r.indexOf('\t'); const [, type, , size] = r.slice(0, t).split(/\s+/); return { type, size: Number(size), path: r.slice(t + 1) }; })
  .filter((e) => e.type === 'blob' && inScope(e.path) && firstArea(e.path) === slug);
const key = (p) => createHash('sha256').update(`lin-4453-area-read|${p}`).digest('hex');
const picked = files.sort((a, b) => (key(a.path) < key(b.path) ? -1 : 1)).slice(0, N);
for (const f of picked) console.log(f.size, f.path);
console.log('TOTAL', slug, 'files', files.length, 'picked', picked.length, 'bytes', picked.reduce((s, f) => s + f.size, 0));
EOF
```

The baseline samples are the output of this snippet at `4b5001ddf`. Run it with `front-end-pages` for the control.

## Reader rubric

The rubric is the dimensions, the scale and the wording in [area-read-reader-prompt.md](area-read-reader-prompt.md). Two passes per area, each by a fresh agent that sees only that area's note and sample. The two passes are A and B, and neither sees the other's output.

**Shared rules.** Readers see only the sampled files and the area's note. They see no tickets, comments, reviews, audits, reports about the codebase's shape, maps or tools. The inputs exclude `docs/plans/`, `docs/reviews/` and `docs/papers/`, and the other area notes.

**The note is scored apart from the code.** The reader scores the code (K1 to K4) and the note (M1 and M2) in separate blocks, so a change to the note cannot be read as a change to the code.

## Verdict criteria (fixed before any reading)

For each area, at each time point, the code score is the mean of the two passes' code means (each pass's code mean is the mean of K1 to K4). Let Δ be the after score minus the before score, for each area.

1. **Noise guard.** At each area and time point, if the two passes' code means differ by 1.0 or more, that read is "not decided". Repeat it with fresh agents; do not re-score the same agents.
2. **Verdict.** With D = Δ(Runs & dispatch) − Δ(Front end: server-rendered pages):
   - D ≥ +0.5: Runs reads better than the control at the same times.
   - D ≤ −0.5: Runs reads worse than the control at the same times.
   - Otherwise: no detectable difference at this threshold.
3. **Note movement is reported on its own.** Δ of the note mean is reported beside D and is not counted in D. Movement in the note alone is reported as note cleanup, never as code improvement. This is the ask's rule: reports distinguish code improvement from note cleanup.
4. **Control moved.** If a sampled control file's blob changed, or any of the four tracked files changed, the control's Δ is flagged. A flagged control does not change the verdict, but it is stated beside it.

The done-when wording, "the area reads better in a blind read after this work than before it, by more than an untouched area read at the same times", maps to verdict 2 with the noise guard passed.

Each area's read at each time point is a comment on LIN-4447, headed exactly:

- `## Area read: Front end: server-rendered pages @ 4b5001ddf`

The heading is never `## Blind read`: the proxy holds that heading to the PR blind-read shape and returns 422.

Each report contains the recorded fields above, both passes' output verbatim, the code mean and note mean of each pass, and the two means for the area. It does not contain the sampled files.

**Citations.** A file is cited as `path@4b5001ddf` (the base commit). The kit and the reader prompt are cited as `docs/plans/survey/area-read.md@<blob>` and `docs/plans/survey/area-read-reader-prompt.md@<blob>`. A report never contains a full PR URL. `landingPrUrls` (`lib/run-ledger.js`) skips only blind reads and survey reports, so an area read that names a PR URL would join LIN-4447's landing.

## Known limits, stated plainly

1. **The sample barely sees the planned work.** One of the 13 planned Runs files is sampled. The read therefore measures the area at large, not the planned changes. A Runs read that does not move can mean the work did not reach the sampled files, not that it failed. The after-read says this.
2. **Most of the move is outside Runs.** The check route is `routes/workspace-api-run-evidence.js` (Web routes). `blindReadStep` (`lib/recommendation-blind-read.js`), `lib/recommendation-facts.js` and `lib/recommendation-live-wait.js` are in LLM & prompts. A Runs-only read sees the new `closeOutDecision` arrive in Runs (piece 1) but not the copies disappear from those files. So "Runs reads better" measures only part of the move. Reports must not claim that duplicate rules outside Runs are gone.
3. **The note is large and shrinks.** Runs' note holds 20 Waiting entries, which later pieces settle, and it is 11.5 KB against the control's 6.4 KB. Scoring the note apart from the code (verdict 3) keeps that from passing as code improvement.
4. **Two passes is a small sample.** Reader variance can be large. The noise guard (verdict 1) is what stops a difference inside the noise from being read as a verdict.
5. **Counting.** The universe excludes JSON such as `lib/runner-kit/contract.json`, and it excludes test files. Both are stated, so a different count is not mistaken for a different sample.
