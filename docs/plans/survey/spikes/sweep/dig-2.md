**G7 (a rework starts on a branch an older session is still working). Worth tracking.**
*How often:* every time it could have happened on 19 Nov. The log names two cases (log.md:4495 for LIN-4494, log.md:4540 for LIN-4495). Dispatch rows in the scratchpad show two more: LIN-4493 (rework `5f77b308` at 15:23 while leftover `2e970021` was live) and LIN-4496 (rework `357d2d07` at 23:52 while leftover `44e568b0` was live, 23:45–23:54). So all four slice 1 pieces that got a "Request Changes" had their rework start while the leftover step was still pushing to the same PR branch. Each rework posted simple-dispatcher's `[duplicate-launch]` alarm (`det_41cd381c.json`, `det_4e9ca286.json`, `ci/d-5f77b308…json`, `out/x_357d2d07.json`). The alarm says another "implementation" session is running. In fact it was the builder's own session resumed for the leftover step, which keeps its `implementation` kind (`duplicate-launch.js:7,61`). Two later alarms (LIN-4553 and LIN-4557 close-out, 24 Nov, against RESUMING sessions) and two against BLOCKED sessions (LIN-4024 in October, LIN-4518) are a different pattern.
*A defect:* yes. The design says the leftover step runs before review: "The build's parent wake is held until that row ends, so an autopilot cannot route `review` before the builder has answered" (`lib/dispatch-leftover.js:5-8`). In the rows that hold did happen. No wake row was minted for build `1a471c63`, while every other stage minted one at once (`d4494.json`). Even so, the same autopilot (`20fdf661`) dispatched review `f0f8fa09` 13 s after the build's `[done]`. That autopilot was in a turn of several hours, and its wakes sat queued and unread (log.md:4462). So it must have seen the `[done]` without the wake; I couldn't see how from the rows. Nothing else stops it. The live-stage wait excludes leftover rows by design ("autopilot, custom, wake, leftover, periodical and abort rows never hold a ticket", `lib/run-live-wait.js:14-17`). It only counts `PROMPT_TEMPLATES` kinds (`lib/recent-runs.js:56`). The duplicate guard is keyed on issue and kind, with a 5-minute window (`lib/dispatch-factory.js:79,287`). simple-dispatcher's check only raises an alarm and never blocks (`dispatcher.js:1301-1327`).
*What it cost then:* two agents pushed to one PR branch at once (LIN-4494: the leftover pushed `fac1392eb`, the rework pushed `caa2463c9` and `a12dcef1b`). The review judged head `b47355c69` without the leftover's commits, including an out-of-scope Jira fix that only the re-review saw (log.md:4497). No rejected push or lost work was recorded.
*Still possible on main:* yes. None of the commits since 19 Nov to `lib/dispatch-leftover*.js` or `lib/run-live-wait.js` (`9a4f3c795`, `d4ad0c5dc`, `4ecd4e986`, `9de9e2048`) adds a leftover row to the wait. No ticket covers it (check-3 searched).
*Cost if left:* whenever an autopilot isn't driven by its wakes, review reads a head the builder is still changing, and a rework then races the leftover's pushes on the same branch. That means a stale review and possible push conflicts on every such task.

**G41 (a flaky scheduler test failed a production deploy). Ignore unless it comes back.**
*How often:* once. The failed job is "Unit tests (proxy, clock +400d)", attempt 1 of run 45546009255 on `c48d18844`, 25 Nov 04:24Z. The failing test is `(e) error containment…` at `tests/unit/scheduler.test.js:288`: "expected the interval to keep ticking past the first throw (at least 2 calls), got 1". Attempt 2 passed. I checked every failed unit job in the last 1,000 Tests runs on all branches (5–27 Nov, about 120 jobs, attempt 1 of each run). This test failed only that once. Among 400 main runs (25 Oct–27 Nov) it is also the only failure of this test.
*A defect:* the test is a small real defect. It relies on wall-clock timing (a 30 ms interval and 15 ms lease, then `sleep(300)` and an expected ≥2 runs, `scheduler.test.js:274-290`), so a slow runner can starve it. The scheduler code itself was not shown broken. "Railway didn't retry" is working as configured: Railway deploys a commit when its CI goes green, and a re-run doesn't trigger a deploy. The same thing happened on 3 Nov with an E2E flake (log.md:280). It cleared itself: the next merge, `d22e7fa`, carried `c48d188` live at about 06:15 (log.md:5337). The real cost was the redeploy question that sat open until 08:25 (log.md:5339), which is a separate issue.
*Still possible on main:* yes. The test is unchanged since `608230b7f` (16 Aug), so it can flake again, but at about 1 in 1,000 runs.

**E20 (four finds from LIN-4423's first blind read, including the unit suite reading `docs/reviews/`). Ignore unless it comes back.**
*How often:* never seen to cause anything. The four finds come from one read (dispatch `434f2d4d`, 12 Nov, `d-br-hand.json`; log.md:3527). The read sorted them as code-shape finds ("2 fix-sized inside, 2 larger inside"), not as bugs.
*A defect:* the `docs/reviews/` read is not a defect. `tests/unit/stability-measures.test.js:992-998` reads the committed reference reading and its declaration README on purpose, so that "a renamed row or measure cannot drift past it unnoticed". Other tests do the same (`periodicals.test.js:879`, `lin-4505-waiting-series.test.js:24`). If the folder moves, the suite fails loudly, which is not a silent trap. `docs/reviews/` is also treated as permanent dated records (`lin-4495-retirement-census.test.js:10`). The other three are harmless. The header in `scripts/stability-measures.mjs:24-28` claims re-runs give the same bytes, yet `readOn` (line 249) records the run day. `describeReference`'s fallback branch (`scripts/stability-measures-core.mjs:501`) is reached only by tests. The `asReference` checks are spread across two files.
*Still possible on main:* all four are still there. The header comment is unchanged since `438d49064` (12 Nov). None has bitten.

**F1 (Harbour's `fable` alias maps to Fable 5.1; the current model is `claude-fable-5-2`). Ignore unless it comes back.**
*How often:* the log notes it once (log.md:3986), and nothing went wrong. Fable was dispatched only a few times (the three 13 Nov essay sessions, log.md:4058; request bodies in `papers/a17b-disp.json`, `a20-disp.json`, `a21-disp.json`, each `model: "fable"`).
*A defect:* a stale fact, of little consequence. `lib/model-routing-harnesses.js:65` maps `fable: 'claude-fable-5-1'`, unchanged since `4f75f00df` (26 Oct). Fable 5.1 is still served, and 5.2 is its cheaper successor ($8/$40 per MTok against $10/$50). The comment above the map (`:52-58`) says it "only prices and names a dispatch that has not reported its model yet", and a run's own reported model wins once it reports. simple-dispatcher passes the bare alias to Claude Code (`executors.js:390`), so the model that actually runs is Claude Code's choice. Harbour's map doesn't decide it. The only effect is a 5.1 name and a price hint about 25% high on an unreported Fable dispatch, for a short while.
*Still possible on main:* yes, as a cosmetic thing. A fix needs the pinned catalog to list 5.2, because `tests/unit/model-routing-harnesses.test.js` prices every mapping against that catalog.
