**A7: a quiet follow-up silencing a parked worker. Call: ignore unless it comes back.** *How often:* never seen. It was reasoned out by LIN-4166's forecast and review (log:397, :422). Every quiet follow-up in the log went to finished workers. The operator adopted that as a rule (log:102) and explicitly kept away from the one parked worker (log:792). *Defect or not:* a known edge of the design, documented rather than guarded. The mechanism is real. simple-dispatcher accepts a follow-up to a BLOCKED or AWAITING_EXTERNAL session, because only RESUMING and EXECUTING count as active (`phases.js:81`, `followup.js:104`). It then points the session's feedback at the follow-up row (`dispatcher.js:336-351`). Harbour mints no wake for anything posted on a `none` row (`lib/dispatch-store.js:3705`). So the worker's real outcome would land without waking its autopilot. The damage is limited, though, not "the autopilot never wakes" as check-1 says. The repoint keeps the original `subscription` and `parentSessionId`, so the parent's failsafe shield lifts once the child is terminal (`reapers.js:1319-1324`). A parked parent is then re-fired by its own 60-minute failsafe (`reapers.js:982-983`). The cost is a delay of up to about an hour. *Still possible:* yes. The entrance only checks that `followUpTo` is present (`lib/dispatch-entrance.js:134-137`), and the only fence is a line in the agent docs (`lib/proxy-instructions.js:782`, "Use it only for a question to a session whose work is finished"). But no code path sends `'none'`: a search of `lib/`, `routes/`, `public/` and `scripts/` found only the gate and comments. The reply box and chat-tools can't set it (LIN-4174, still Backlog). So it takes a hand-written API call that goes against the docs.
